Refinamento Técnico

Normalmente feito pelo PO, mas o dev recorre a estes comandos quando o card chega sem User Story, sem caderno E2E, ou é um bug sem diagnóstico.

/refinar-feature <EFC-XXXX>
O que faz Dispara um subagente de pesquisa que lê o card no Jira, verifica handoff de design (zip anexo) e explora o repositório. Com isso, redige uma User Story estruturada (contexto, "Como… quero… para que…", critérios de aceite numerados, regras de negócio e — se houver — um bloco de Complementos Técnicos). Pergunta sobre onde busca/paginação são processadas quando a feature envolve listagem. Apresenta para aprovação antes de gravar qualquer coisa.
Quando usar Quando o card chega sem User Story definida — antes de qualquer planejamento técnico.
Saída Atualiza a descrição do card no Jira (formato ADF) e salva Docs/user-story-EFC-XXXX.md localmente — é esse arquivo que o /planejar-implementacao vai ler depois.
Pré-requisitos Variáveis JIRA_BASE_URL, JIRA_USER e JIRA_API_TOKEN exportadas (! export NOME=valor).
/documentar-e2e <EFC-XXXX>
O que faz Gera um caderno de testes em Gherkin (Given/When/Then), em linguagem de negócio pura — sem botão, modal, aba, status HTTP ou nome de classe. Lê Docs/user-story-EFC-XXXX.md se existir, senão busca no Jira. Apresenta para aprovação, depois anexa ao card e remove o arquivo local.
Quando usar Após a User Story aprovada — serve de contrato de aceite para QA/UAT. Não confundir com a automação Playwright (/criar-automacao), que é técnica e vive no repositório.
/identificar-bug <EFC-XXXX>
O que faz Garante que o repositório está em master atualizado e sem alterações pendentes, depois dispara um subagente que lê o card (incluindo anexos) e explora o código para entender o fluxo com problema. Gera dois documentos aprovados separadamente: um bug report em linguagem de negócio (passos de reprodução, impacto, comportamento esperado) e um caderno de testes E2E com cenário de regressão.
Quando usar Ao receber um card de bug, antes de abrir a branch de correção. Serve como substituto válido dos CAs para o /planejar-implementacao.
Planejamento Técnico

Ponto de entrada padrão do dev quando a User Story já existe.

/planejar-implementacao <EFC-XXXX> mudou
O que faz Um subagente lê o spec (Docs/user-story-EFC-XXXX.md, ou Jira, ou bug report) e avalia se há CAs suficientes. Com os CAs e complementos técnicos confirmados, outro subagente explora o repositório e monta um plano faseado respeitando a arquitetura em camadas (Domain → Domain.Services → Infra → API → Frontend). Cada fase indica o CA correspondente (ou "infraestrutura") e, quando aplicável, qual comando de scaffolding seguir.
Regra nova Toda fase de frontend implica uma fase de automação E2E (/criar-automacao). O plano sempre termina com uma fase de /revisar-comentarios, depois de todo o desenvolvimento e teste — mesmo que nenhuma fase anterior tenha mexido em comentários.
Saída Docs/plano-tecnico-EFC-XXXX.md (fases com status pendente/concluída) e Docs/criterios-aceite-EFC-XXXX.md.
Pré-requisitos User Story aprovada (idealmente via /refinar-feature).
Implementação

O comando central é /executar-plano; os comandos de scaffolding abaixo podem ser chamados por ele (como subagente) ou diretamente pelo dev para uma necessidade pontual.

/executar-plano <EFC-XXXX> mudou
O que faz Lê Docs/plano-tecnico-EFC-XXXX.md, confirma que o branch não é protegido (master/develop/homolog/production) e executa as fases pendentes uma por vez, aguardando confirmação explícita entre elas. Quando a fase indicar um padrão de scaffolding, lê o comando correspondente do disco antes de implementar — nunca replica de memória.
Fluxo final
  • 4 — Build e testes: dotnet test (backend), npm run build + lint + Jest da feature (frontend), e a suíte E2E da feature se houve alteração de tela
  • 5 — Revisão de comentários: roda /revisar-comentarios sobre a feature inteira, não só o que este plano mudou
  • 6 — Commit: só após confirmação explícita do usuário
Pré-requisitos Plano técnico existente. Branch feature/EFC-XXXX-descricao (ou hotfix/...) ativo.
/criar-entidade <NomeDaEntidade>
O que faz Scaffolding completo de entidade de domínio: classe (BaseEntity/StatefulEntity), interface e implementação de repositório, mapping EF Core, fixture Bogus para testes. Atualiza navegações reversas nas entidades relacionadas.
Inputs Nome (PascalCase), tipo (Base/Stateful), campos com tipo e relações.
/criar-filtro <Funcionalidade> mudou
O que faz Scaffolding de um filtro em cascata: enum de passos, DTO de request, repositório de filtro, FilterService com um único método Filter(request, passo) (switch por passo — não mais um método por passo), ValidacaoService, controller, configuração/service Angular do filtro e página de listagem (corpo vazio). Os passos 6 e 8 invocam /criar-service como subagente para gerar o service e o validador. Termina com testes de integração do FilterService.
Quando usar Quando a feature tem tela de listagem com filtro hierárquico (ex.: Rede → Escola → Turma).
/criar-exportacao <Funcionalidade> mudou
O que faz Adiciona exportação Excel a uma feature que já tem filtro: DTO de exportação, GetParaExport no repositório, Exportar{Funcionalidade}Service (via subagente /criar-service), endpoint /export e botão de exportação no Angular.
Pré-requisito obrigatório {Funcionalidade}FilterRequest já precisa existir — se não existir, o comando interrompe e pede para rodar /criar-filtro primeiro.
/criar-service <Funcionalidade> <NomeService> mudou
O que faz Cria interface e implementação de um service de domínio: primary constructor C# 12, ServiceResult<T>, validação procedural, sem Include(), sem query em loop. Pode ser chamado diretamente ou como subagente por criar-filtro/criar-exportacao.
Regras novas Service público acima de ~200 linhas vira orquestrador, delegando etapas para services por papel (Dados*, Validacao*, Efeitos*). Proibido tipo aninhado (record/class privados) — DTO vai para Domain/DTO. Update direto vs. Disable+Insert conforme precisar reter histórico.
/criar-testes <NomeService | Feature> mudou
Escopo Agora cobre apenas Jest (frontend) e integração .NET (backend). A automação E2E com Playwright foi extraída para /criar-automacao.
O que faz Frontend: testes de serviço (mock de ApiClient) e de componente (lógica pura extraída para classe local, sem TestBed). Backend: classe herdando BaseTest, seed via SeedDatabase, cobrindo caminho feliz, ramificações e variações de permissão. Apresenta cenários para aprovação antes de criar arquivos.
/criar-automacao <feature> novo
O que faz Cria ou atualiza testes E2E Playwright em frontend/tests/e2e/<feature>/. Valida que o branch não é protegido, explora a feature (service, templates, rotas) e, se o usuário não indicou cenários específicos, propõe o que automatizar — incluindo testes defasados ou redundantes a corrigir — antes de implementar.
Regra central Um caminho feliz por feature; demais testes só cobrem o que é mutuamente exclusivo dele. Importa sempre de tests/fixtures (nunca @playwright/test direto). Todos os endpoints mockados. Atenção ao debounce do filtro (300ms) como causa recorrente de flakiness.
Quando usar Toda fase de frontend do plano técnico passa por aqui — e também é o passo final de validação visual de qualquer alteração de tela.
Qualidade — antes do PR

/revisar-comentarios já roda automaticamente como última fase de /executar-plano; /analisar-sonar é manual, rode antes do push.

/revisar-comentarios <Feature> novo
O que faz Lê CLAUDE.md e os README.md (raiz/backend/frontend) para extrair o critério vigente de comentário — nunca de memória. Mapeia todos os arquivos da feature (backend e frontend), classifica cada comentário em manter / reescrever / remover, aplica as mudanças preservando encoding e indentação, e roda build+testes para garantir que só comentário foi tocado.
Quando usar Como passo final de /executar-plano, ou isoladamente em qualquer feature existente. Abrange a feature inteira, não só o que uma sessão mudou.
/analisar-sonar [backend|frontend|ambos] [full] novo
O que faz Roda o scanner SonarQube local comparando o branch atual com a base (ou análise completa com full), aguarda o processamento e relata Quality Gate, bugs, vulnerabilidades, code smells novos e security hotspots a revisar — com arquivo e linha de cada issue quando houver.
Pré-requisitos SONAR_HOST_URL, SONAR_TOKEN, SONAR_PROJECT_KEY_BACKEND/_FRONTEND no bloco env de .claude/settings.local.json. Scanners (dotnet-sonarscanner, sonar-scanner) instalados globalmente.
Quando usar Antes do push — bugs, vulnerabilidades e hotspots devem ficar em zero.
Revisão de Código
/analisar-pr [branch | nº-PR] [EFC-XXXX | --criterios] mudou
O que faz Analisa o diff entre dois branches (ou de um PR do GitHub via número) e gera Docs/revisao-pr.md com três seções: Conformidade com o Spec (CA por CA, considerando automação E2E como "testado"), Backend (N+1, projeções, autenticação, UnitOfWork, etc.) e Frontend (tipagem, erros HTTP, standalone, modais, guards).
Novo: correção automática Ao final, pergunta se deseja disparar um subagente que avalia cada achado de forma independente, aplica os que concorda e justifica os que rejeita.
Modos de uso
  • /analisar-pr 212 — analisa o PR #212 do GitHub (gh pr view)
  • /analisar-pr master EFC-1234 — compara branch atual com master, valida os CAs do card
  • /analisar-pr master --criterios — pede os CAs manualmente antes de analisar
Merge
/merge-branch <branch-origem> mudou
O que faz Traz as mudanças do branch informado para o branch atual (destino). Classifica cada conflito entre resolvível automaticamente e requer decisão humana, apresentando a triagem completa antes de resolver qualquer um. Roda build de verificação antes do commit do merge.
Passo novo — 4.5 Após o merge (com ou sem conflito), verifica perdas silenciosas do auto-merge: arquivos deletados que só existiam no destino, e linhas truncadas em arquivos auto-mergeados sem conflito. Regra absoluta: nunca gerar, inferir ou colocar NotImplementedException() em código que pareça ausente — sempre verificar no histórico git antes.
Restrições
homolog nunca pode ser a origem. Merges para production só são permitidos a partir de master.

_e2e-execucao.md novo Como rodar a suíte E2E de uma única feature e o que fazer quando a falha é de setup/autenticação (não insistir, reportar e validar só a compilação dos specs).

No Claude Code, use ! export NOME=valor para exportar sem sair da sessão. As variáveis de Sonar ficam em .claude/settings.local.json e só valem a partir do início de uma nova sessão.
