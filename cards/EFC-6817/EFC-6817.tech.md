# Plano Técnico — EFC-6817

> Gerado em: 2026-09-15

## Contexto

O refinamento de EFC-6817 define 12 critérios de aceite sobre o Painel do Aluno (`estrutura-pedagogica`, `frontend/src/app/features/painel-aluno/`): 10 ajustes visuais/UX e 2 correções de bug. É um card 100% frontend Angular — não há alteração de backend, entidades, banco ou scripts SQL necessária para nenhum dos CAs (confirmado ponta a ponta para CA-11).

## Convenções aplicáveis

1. Todo componente novo é `standalone: true`, sem NgModule, com imports explícitos.
2. Antes de estilizar/criar qualquer elemento de UI, verificar o catálogo `src/app/features/exemplos/tela-base/` — não existe segmented control lá nem em `src/shared`; precisa ser criado e o catálogo atualizado na mesma mudança (regra do README).
3. Modal vs. side panel: já existe padrão de referência pronto em `ficha-medica-edicao.component.ts/html` (`SidePanelComponent`: `[show]`, `[preventClose]`, `[topInfo]`, `[title]`, `(closeEvent)`, `(closeAttempt)`, diretiva `sidePanelFooter`, fluxo `hasChanges`/`tentarFechar()`/`onCloseAttempt()` com modal de confirmação de descarte).
4. Não adicionar comentários não pedidos no código de aplicação.
5. Testes Jest (`criar-testes.md`): usar classe local espelhando a lógica, nunca `TestBed`/import direto do componente Angular.
6. Testes E2E (`criar-automacao.md`): fixtures de `tests/fixtures`, helpers de `tests/helpers/ui`, um teste por regra (sem repetir caminho feliz), mockar todos os endpoints, nunca `page.goto()` com barra inicial. Sempre a última fase.
7. Tokens de cor: variáveis `--color-*` não são declaradas no frontend (injetadas por shell externo) — usar sempre `var(--token, $fallback-scss)`. Nome real do token do CA-01 é `--color-neutral-dark-3` (com hífen), não `--color-neutral-dark3` como grafado no card.
8. Nunca ligar `[options]`/`[request]` a getters que recriam referência a cada change detection.

## Critérios de Aceite

CA-01 a CA-12 conforme `EFC-6817.refinamento.md` (pílulas do Resumo Inteligente; segmented control em Pedagógico e em Frequência/Comportamento; header/corpo de Objetivo e Norteadores; fundo/título dos boxes de Atendimento; reordenação do bloco final de Atendimento; contraste em Anamnese; contraste em Ocorrências/Atendimento; modal de e-mail de Ocorrência; Documentos como side panel; bug do botão de editar Ficha Médica; bug da prévia de e-mail de Atendimento).

### Fase 7 — Bugs: botão de editar Ficha Médica e prévia de e-mail _(CA-11, CA-12)_

**Status:** pendente

- **CA-12:** em `atendimento-email-previa.service.ts` (`obterTemplate()`, linhas 54-64), o template é cacheado via `shareReplay(1)` sobre um `catchError(() => of(null))` — se a primeira chamada falhar, o `null` fica cacheado permanentemente no singleton `providedIn: 'root'`, e `atualizarPreviaEmail()` (linha 935) nunca mais preenche a prévia, mesmo satisfazendo RN-03. Corrigir para não cachear falha (ex.: mover o `catchError` para fora do operador que alimenta o `shareReplay`, ou resetar `template$` quando o resultado vier `null`). **Validar a hipótese reproduzindo o bug antes de codar** — se a causa real for outra (ex.: dado ausente em `motivosAtendimento`/`tiposAtendimento` no momento do debounce), o fix proposto não resolve sozinho.
- **CA-11:** nenhum defeito de código foi localizado — toda a cadeia (`PermissaoService.cs` → `ValidacaoService.cs` → `PainelAlunoPermissoesResponse` → `painel-aluno.service.ts` → `painel-aluno-state.service.ts` → `ficha.component.ts` → `ficha-medica-resumo.component.html`) já está implementada e testada corretamente. Esta fase deve começar por **investigação dirigida** (reproduzir com o usuário/perfil relatado, checar resposta real de permissões, confirmar se a Funcionalidade `PainelAluno_FichaMedica_Editar` está associada ao perfil) antes de decidir se é fix de código ou correção de dado de permissão (nesse caso, script SQL em `cards/EFC-6817/sql/`, conforme convenção do projeto — não seria alteração de C#/TS).
