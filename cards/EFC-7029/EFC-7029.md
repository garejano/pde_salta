# EFC-7029 — Novo modelo de autenticação do SaltaId

## 1. Contexto e Motivação

O login do Atlas recebia do SaltaId o token de acesso diretamente na URL de retorno, um modelo antigo que expõe o token no endereço e no histórico do navegador. O SaltaId passou a oferecer o fluxo com código de autorização e PKCE: o retorno traz só um código de uso único, e o token é obtido numa troca protegida por uma chave gerada pelo próprio navegador. Esta atividade migra o login do Atlas para esse modelo, revê o comportamento de cada situação de acesso (login concluído, usuário sem acesso, falhas na validação, sessão vencida, logout) e padroniza o nome "Salta Id" no lugar do antigo "Eleva Id".

**User Story Principal:** Como usuário do Atlas, quero entrar pelo SaltaId de forma segura e ser levado à tela certa em cada situação de acesso, para que meu token não fique exposto e eu sempre saiba o que fazer quando meu acesso for recusado ou expirar.

## 2. Critérios de Aceitação

### Login

- **CA-01** — Ao entrar, o usuário é levado à tela de login do SaltaId e, ao voltar, o Atlas conclui o login sem que o token de acesso apareça na URL em nenhum momento.
- **CA-02** — Cada tentativa de login é única: um retorno do SaltaId que não corresponda ao login iniciado naquele navegador é recusado e leva à tela de falha de autenticação.
- **CA-03** — O código recebido no retorno só pode ser usado uma vez; recarregar ou reabrir a URL de retorno não refaz o login.
- **CA-04** — Concluído o login, o usuário vai para a página inicial do Atlas. Se o login começou na tela de sessão expirada, ele volta à tela em que estava.
- **CA-05** — A sessão iniciada no Atlas vale também para o sistema pedagógico (/ped), sem novo login.

### Usuário sem acesso

- **CA-06** — Se o usuário autenticado no SaltaId não tiver acesso ao Atlas, ele vê a mensagem "Você não tem acesso ao Atlas!", tem a sessão encerrada no Atlas e no SaltaId e volta à tela de login, sem ficar preso em ciclo de redirecionamentos.
- **CA-07** — Essa verificação termina antes de o usuário ser levado à página inicial.

### Acesso às telas

- **CA-08** — Ao abrir uma tela do Atlas sem sessão ou com a sessão vencida, o usuário vai para a tela de sessão expirada sem nenhuma consulta ao servidor; o botão "Entrar novamente" inicia um novo login e, ao concluí-lo, volta à tela em que o usuário estava.
- **CA-09** — Com sessão válida, o Atlas confirma os dados do usuário uma vez ao abrir a aplicação; a navegação entre telas não repete essa confirmação.
- **CA-10** — Se a confirmação dos dados do usuário demorar além do limite, o usuário vê a tela de falha de autenticação com a mensagem de tempo esgotado e o botão "Tentar novamente", que leva de volta à tela pretendida.
- **CA-11** — Outras falhas na confirmação levam à mesma tela, com mensagem genérica e o mesmo "Tentar novamente".

### Durante o uso

- **CA-12** — Se a sessão vencer durante o uso, a próxima ação recusada pelo servidor leva à tela de sessão expirada; o "Entrar novamente" volta à tela em que o usuário estava após o login.
- **CA-13** — Se o servidor recusar uma ação por falta de permissão, o usuário vai para a tela de acesso não autorizado.
- **CA-14** — A tela de acesso não autorizado diferencia o usuário que tem acesso ao Atlas (orienta a usar o menu para outra tela) do usuário sem acesso ou cujo acesso não pôde ser verificado; nos dois casos há a opção de sair.

### Logout

- **CA-15** — Sair, pelo menu do usuário ou pela tela de acesso não autorizado, encerra a sessão no Atlas, no sistema pedagógico e no SaltaId, limpa os dados locais da sessão e leva ao logout do SaltaId.

### Nomenclatura

- **CA-16** — Telas, menus e mensagens do Atlas usam o nome "Salta Id"; o termo "Eleva Id" não aparece para o usuário.

### Desenvolvimento local

- **CA-17** — Em ambiente local, o desenvolvedor pode rodar o Atlas sem o SaltaId, assumindo automaticamente um usuário configurado, com as mesmas permissões que esse usuário teria num login real. Fora do ambiente local, essa opção nunca é aceita.

### Regras de Negócio

| Situação | Destino |
|---|---|
| Login concluído, com acesso ao Atlas | Página inicial |
| Login concluído, sem acesso ao Atlas | Mensagem "Você não tem acesso ao Atlas!", saída do Atlas e do SaltaId, novo login |
| Retorno do SaltaId que não corresponde ao login iniciado | Falha de autenticação |
| Falha ao trocar o código pelo token | Falha de autenticação |
| Tela aberta sem sessão ou com sessão vencida | Sessão expirada (sem consulta ao servidor) |
| Confirmação do usuário sem usuário ou recusada | Sessão expirada |
| Confirmação do usuário com tempo esgotado | Falha de autenticação (tempo esgotado), "Tentar novamente" para a tela pretendida |
| Confirmação do usuário com outra falha | Falha de autenticação (genérica), "Tentar novamente" para a tela pretendida |
| Ação recusada por sessão vencida | Sessão expirada |
| Ação recusada com sessão local ainda válida | Acesso não autorizado, sem guardar a tela recusada; a saída é pelo menu |
| Ação recusada por falta de permissão | Acesso não autorizado, sem guardar a tela recusada; a saída é pelo menu |

### Complementos Técnicos

- **Fluxo:** OAuth 2.0 Authorization Code + PKCE (RFC 7636). `code_verifier` (64 bytes) e `state` (32 bytes) em base64url, guardados no `sessionStorage` e descartados no retorno, com ou sem sucesso. `code_challenge` S256. Sem `client_secret` no frontend.
- **Ida:** `{SALTA_ID}/?response_type=code&client_id&redirect_uri&scope=openid profile email&state&code_challenge&code_challenge_method=S256`. O `redirect_uri` é `{origem}/{base}/auth/salta-id`, ou `{origem}/auth/salta-id` nos ambientes servidos na raiz (hot e hot-homolog). Vai sem parâmetros e precisa estar cadastrado no SaltaId para o `client_id` de cada ambiente.
- **Troca do código:** `POST {SALTA_ID}/api/authorize`, form-urlencoded (`GrantType`, `clientId`, `code`, `redirectUri`, `codeVerifier`), por um `HttpClient` sobre o `HttpBackend`, sem os interceptors da aplicação. Resposta com `accessToken` e `expiresIn`.
- **Armazenamento:** validade calculada a partir de `expiresIn`, em horário local. Token em `usuarioAutenticado.ElevaId` e `access_token` no `localStorage`, compartilhado com o `/ped`. O JSON do usuário autenticado vem do `/ped` sem alteração.
- **Nomes mantidos como `ElevaId`:** os campos `ElevaId` e `LoginComElevaId` fazem parte do contrato com o `/ped`; também a coluna `Usuario.ElevaId` no banco, a coluna `UsuarioAuthToken.ElevaIdAuthToken` (na entidade, a propriedade `SaltaIdAuthToken`, mapeada para essa coluna) e as permissões legadas do `/ped`.
- **Configuração do frontend:** `SALTA_ID` e `SALTA_ID_CLIENT_ID` em cada `environment*.ts`, no lugar das chaves `ELEVA_ID`. O `client_id` de cada ambiente vem do cadastro no SaltaId.
- **Configuração do backend:** `Project.SaltaId`. Os parâmetros publicados (AWS Secrets Manager) precisam usar essa chave.
- **Backend:** o token é validado localmente pela tabela `UsuarioAuthToken`, que guarda o token registrado e a validade. Sem registro válido, o token é revalidado na API do SaltaId (`me`) e um novo `UsuarioAuthToken` é gravado.
- **Bypass local:** `IsLocalhost` + `SaltaId.BypassEnabled` + `SaltaId.BypassUserId`. A requisição é autenticada como o `BypassUserId`, com os acessos reais desse usuário.
- **Correções incluídas:** a tela de retorno aguarda o carregamento do usuário antes de redirecionar (CA-07); o logout da tela de acesso não autorizado usa o mesmo fluxo do menu (CA-15).
- **Falhas de autenticação:** tela de falha de autenticação (`falha-autenticacao`), com motivo `tempo-esgotado` quando o erro for timeout. Uma resposta 401 com o token local ainda válido leva ao acesso não autorizado; com o token vencido, à sessão expirada.
- **E2E:** o setup obtém o token direto na API do SaltaId (usuário técnico, `client_credentials`) e o grava no `localStorage`; a tela de login do SaltaId e o PKCE não são exercitados pela automação.

## 4. O Que Precisa Ser Feito

Migrar o fluxo de login do portal Atlas do modelo antigo (token na URL de retorno) para OAuth 2.0 Authorization Code + PKCE, incluindo:
- Novo fluxo de ida/retorno do SaltaId com `code_verifier`/`state`/`code_challenge`
- Troca do código por token via `POST {SALTA_ID}/api/authorize`
- Revisão de todas as telas de erro de sessão/autenticação (sessão expirada, falha de autenticação com motivo de timeout, acesso não autorizado)
- Validação de token no backend via tabela `UsuarioAuthToken`, com revalidação na API do SaltaId quando necessário
- Bypass de login em ambiente local (`SaltaId.BypassEnabled`)
- Renomeação de "Eleva Id" para "Salta Id" nas telas, mantendo os nomes técnicos legados (`ElevaId`) no contrato com `/ped` e no banco
- Ajuste do setup de autenticação E2E para obter token via `client_credentials`

A descrição do card já está estruturada como User Story completa com CAs numerados e Complementos Técnicos — equivalente ao que o comando `/refinar-feature` produziria.
