# EFC-6542 — Possibilitar a seleção de múltiplos diagnósticos

## 1. Contexto e Motivação

O sistema permite registrar o diagnóstico de alunos com Necessidades Educacionais Especiais (NEE) por meio de uma seleção de tipos de transtorno. Atualmente, o campo aceita apenas uma opção, mas é comum que estudantes tenham mais de um diagnóstico simultaneamente — como TDAH e dislexia, ou TEA e deficiência intelectual. A limitação impede o registro completo do perfil clínico do aluno.

**User Story:** Como gestor responsável pelo cadastro de NEE de alunos, quero selecionar dois ou mais diagnósticos para o mesmo aluno, para que o perfil clínico do estudante fique registrado de forma completa no sistema.

---

## 2. Critérios de Aceitação

- **CA-01:** O sistema deve permitir selecionar dois ou mais diagnósticos simultaneamente para um mesmo aluno.
- **CA-02:** Os diagnósticos selecionados devem ser salvos e permanecer visíveis no registro de NEE do aluno.
- **CA-03:** Deve ser possível adicionar ou remover um diagnóstico individualmente sem afetar os demais já selecionados.
- **CA-04:** Ao selecionar TEA como um dos diagnósticos, o campo de subtipo (Nível 1, 2 ou 3) deve ser preenchido obrigatoriamente antes de salvar.
- **CA-05:** A opção "Outro" deve continuar funcionando mesmo quando outros diagnósticos já estiverem selecionados, incluindo seu campo de complemento de texto.
- **CA-06:** O registro de NEE do aluno deve exibir todos os diagnósticos selecionados de forma clara, incluindo o subtipo quando aplicável.

## 7. Implementação (2026-08-18)

**Decisão de design:** os campos legados `AlunoNecessidadesEspeciais.TipoTranstornoId`/`TipoTranstorno`/`TipoTranstornoOutro` foram **mantidos intactos** (mesmo padrão de compatibilidade retroativa já usado em EFC-6381 para o campo `Diagnostico` livre) — servem apenas para leitura de registros salvos antes desta feature. Novos salvamentos passam a usar exclusivamente a nova coleção `Diagnosticos`. Ao carregar um registro legado sem `Diagnosticos`, o frontend migra automaticamente o valor único para a nova estrutura (1 linha), então o próximo salvamento já grava no formato novo.

**Backend** (`c:/projects/notas/backend/`):
- Nova entidade `AlunoNecessidadesEspeciaisTipoTranstorno` (`Notas.Domain/Entities/Base/`) — tabela de relação N:N com `AlunoNecessidadesEspeciaisId`, `TipoTranstornoId` e `TipoTranstornoOutro` por entrada (permite "Outro" funcionar mesmo com múltiplos diagnósticos selecionados, CA-05).
- Mapeamento EF `AlunoNecessidadesEspeciaisTipoTranstornoMap.cs` (`Notas.Infra/Mapping/Base/`).
- `AlunoNecessidadesEspeciais.cs` — nova coleção `Diagnosticos`.
- Novos DTOs `AlunoNeeDiagnosticoResponse`/`AlunoNeeDiagnosticoSaveRequest`; `GetResponse`/`SaveRequest` ganharam `Diagnosticos`/`List<AlunoNeeDiagnosticoSaveRequest>` (o campo único `TipoTranstornoId` foi removido do `SaveRequest` — só existe mais no `GetResponse`, como legado).
- `AlunoNecessidadesEspeciaisCreateService.cs` — grava a coleção via navegação EF (insert em cascata na mesma `SaveChanges`, sem precisar do Id do pai antecipadamente).
- `AlunoNecessidadesEspeciaisRepository.cs` — `GetResponse` projeta `Diagnosticos`; `GetByPessoa` agora inclui (`Include`) a coleção para permitir comparação de alterações.
- `NEESaveNecessidadesService.cs` — `PossuiAlteracao` compara as duas listas de diagnósticos (ordenadas por Id) em vez do campo único.
- Script SQL: `cards/EFC-6542/sql/01_create_AlunoNecessidadesEspeciaisTipoTranstorno.sql`.
- Teste novo `Create_Persiste_Multiplos_Diagnosticos` em `AlunoNecessidadesEspeciaisCreateServiceTests.cs`, exercitando o mapeamento EF de ponta a ponta com o provider InMemory. Build + suíte de testes de NEE (19 testes) rodados: todos passando.
- **Não implementado (fora do escopo explícito das CAs):** validação de backend para impedir que o Id de um nó pai com subitens (ex.: "TEA" sem escolher o nível) seja salvo diretamente — CA-04 é hoje garantida só pelo frontend (mesma limitação que já existia no single-select antes desta story). Também não foi alterada a exportação Excel (`NecessidadesEspeciaisExport_Get.sql`), que continua mostrando apenas o diagnóstico legado — CAs da story não cobrem o relatório.

**Frontend** (`c:/projects/notas/frontend/`):
- `models/aluno-nee.model.ts` — novas interfaces `AlunoNeeDiagnosticoSaveRequest`/`AlunoNeeDiagnosticoResponse`; `AlunoNeeSaveRequest.diagnosticos` e `AlunoNecessidadesEspeciaisResponse.diagnosticos` (campos legados `tipoTranstorno`/`tipoTranstornoOutro` mantidos só no response).
- `edicao-nee/edicao-nee.component.ts` — campo único `tipoTranstornoPaiId/Id/Outro` virou `FormArray` `diagnosticos`; cada linha tem sua própria lógica de subitens/```OUTROS`` (replicada por linha via `criarDiagnosticoGroup`); métodos `adicionarDiagnostico()`/`removerDiagnostico(i)` (CA-03); `preencherCampoTipoTranstorno()` migra automaticamente o legado para 1 linha quando `diagnosticos` vier vazio.
- `edicao-nee.component.html` — bloco "Tipo de transtorno" reescrito com `formArrayName="diagnosticos"`, um card por diagnóstico (select + subtipo condicional + campo "outro" condicional + botão remover) e botão "Adicionar diagnóstico".
- `detalhes-nee/detalhes-nee.component.ts`/`.html` — exibe a lista de `diagnosticos` quando presente; cai para o campo legado único (`tipoTranstorno`/`tipoTranstornoOutro`) quando o registro é antigo.
