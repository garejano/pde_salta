# Plano Técnico — EFC-6726

> Gerado em: 2026-08-18

## Contexto

O frontend do `estrutura-pedagogica` está na versão 20.3 do Angular, com bootstrap ainda via `NgModule` clássico (`app.module.ts`, 27 módulos legados sob `features/`) coexistindo com componentes `standalone`. Duas dependências de UI (`ng-select`, `ng-bootstrap`) estão travadas em peer `^20.0.0` e precisarão de bump de major própria. A investigação encontrou indícios fortes de que os únicos dois pontos de uso real dessas libs (`NgSelectFieldComponent` e `DaterangepickerFieldComponent`) são código órfão, sem nenhuma referência em templates — restando apenas `portal-menu*` (código local) como uso genuíno de `ng-bootstrap`. Não há gate de testes no pipeline de CI (`buildspec.yml`); a suíte (86 specs Jest + 145 specs Playwright) precisa ser validada manualmente.

## Convenções aplicáveis

1. Não adicionar comentários no código de aplicação (exceção: testes).
2. Todo componente novo deve ser `standalone: true` — não é necessário migrar os módulos legados existentes para standalone neste card (fora de escopo).
3. Priorizar shared/dynamic components em qualquer HTML tocado.
4. Testes unitários Jest não importam o Angular real (classes "Logic" espelho) — convenção que reduz o risco estrutural do upgrade sobre a suíte unitária.
5. Suíte E2E (Playwright) depende de app + backend rodando localmente com sessão SaltaId real (`npm run test:e2e:auth` + `npx playwright test`), não é isolada.

## Critérios de Aceite

- **CA-01:** A aplicação frontend compila e é executada utilizando Angular 22.
- **CA-02:** As bibliotecas de terceiros (`ng-select`, `ng-bootstrap`) atualizadas para versões compatíveis com Angular 22.
- **CA-03:** Sem regressão visual ou funcional perceptível em nenhuma tela existente.
- **CA-04:** Suíte de testes automatizados (unitários + E2E) executada manualmente e passando.
- **CA-05:** Pipeline de build/deploy (`buildspec.yml`) continua funcionando normalmente.

## Fases

### Fase 1 — Investigação e remoção de código órfão _(CA-02, CA-03)_

**Status:** concluída

Confirmar se `frontend/src/core/components/ng-select-field/` e `frontend/src/core/components/daterangepicker-field/` (e os 5 arquivos `.scss` com overrides `::ng-deep` de `ng-select` em `movimentacao-pedagogica`) são genuinamente órfãos — sem nenhuma referência em templates de features. Se confirmado, remover esses componentes e seus imports em `core.module.ts` (`NgSelectModule`, `NgbModule`/`NgbDatepickerI18n`, se não sobrar nenhum outro consumidor). Isso reduz o raio de impacto do upgrade dessas duas libs a praticamente zero, restando só `portal-menu*.component.html` como consumidor real de `ng-bootstrap`.

---

### Fase 2 — `ng update` incremental 20 → 21 → 22 _(CA-01)_

**Status:** concluída

> Bloqueio encontrado e resolvido: Angular CLI 22 exige Node.js ≥ 22.22.3 (ou 24.15.0/26.0.0); a máquina tinha Node v22.18.0. Node.js atualizado globalmente para v22.23.2 (mesma major, menor impacto em outros projetos) com aprovação do usuário.

Executar a migração do Angular **um major por vez** (nunca saltar direto 20→22), rodando `ng update @angular/core@21 @angular/cli@21` (e `@angular/cdk@21`) primeiro, aplicando os schematics automáticos e corrigindo erros de compilação, depois repetindo o processo para a versão 22. Arquivos tocados: `frontend/package.json`, `frontend/package-lock.json`, `frontend/angular.json`, `frontend/tsconfig.json` (checar `target`/`experimentalDecorators` frente às novas exigências), `frontend/src/polyfills.ts` (`zone.js` — app permanece zone-based, sem migração para zoneless neste card). Aproveitar para remover o target `architect.test` (Karma) de `angular.json`, que referencia um `karma.conf.js` inexistente e pode causar erro em algum schematic.

---

### Fase 3 — Atualização de `ng-select` e `ng-bootstrap` _(CA-02)_

**Status:** concluída

> `ng-select` foi removido inteiramente (código órfão eliminado na Fase 1). `@ng-bootstrap/ng-bootstrap` atualizado para `^21.0.0` (peer Angular 22). Também identificado durante a execução que `@fortawesome/angular-fontawesome` tinha o mesmo problema de peer (não estava no levantamento original) — atualizado para `^5.1.0`.

Atualizar `@ng-select/ng-select` e `@ng-bootstrap/ng-bootstrap` para as menores versões que declarem suporte a peer `@angular/core@22` (checar changelog de cada lib antes de fixar a versão — hoje ambas travam em `^20.0.0`). Se a Fase 1 confirmar a remoção do código órfão, esta fase se reduz a validar apenas `portal-menu*.component.html` (uso local de `ngb-*`). Caso `ng-select` sobreviva em algum ponto não identificado, revalidar seletores/DOM gerado.

---

### Fase 4 — Revisão dos módulos legados (`NgModule`) _(CA-01, CA-03)_

**Status:** concluída

> `HammerModule` confirmado removido de `@angular/platform-browser` no Angular 22 — removido de `app.module.ts` (sem uso real de gestos Hammer.js na aplicação). `BrowserAnimationsModule` segue funcionando mas está deprecado (sugestão de migração futura para `provideAnimations()`, fora do escopo deste card). Nenhum outro símbolo removido/quebrado encontrado na varredura dos imports `@angular/*` dos módulos legados.

Revisar `app.module.ts` e os 27 `*.module.ts`/`*-routing.module.ts` legados sob `features/` quanto a APIs removidas/deprecadas entre Angular 20 e 22 — atenção especial a `HammerModule` (`@angular/platform-browser`), historicamente em trilha de remoção, usado hoje em `app.module.ts`. Não é necessário migrar esses módulos para `standalone`/`bootstrapApplication` — apenas garantir que compilam e funcionam na v22. Módulos de outro time (`features/folha/`, `features/movimentacao-pedagogica/`) só devem ser tocados se o erro de compilação exigir.

## Restrições e riscos

- Sem gate de testes no CI — CA-04 depende inteiramente de disciplina manual; risco de regressão passar para produção sem detecção automática.
- `ng-select`/`ng-bootstrap` podem não ter, no momento da implementação, uma versão publicada com peer compatível para Angular 22 — validar antes de iniciar a Fase 3.
- Arquitetura híbrida `NgModule` + `standalone`: maior superfície de risco de breaking change está nos 27 módulos legados, não na lógica de negócio.
- `HammerModule` em uso em `app.module.ts` — validar se ainda existe no Angular 22.
- Possível código morto (`NgSelectFieldComponent`, `DaterangepickerFieldComponent`, SCSS de `ng-select`) infla artificialmente o risco percebido — confirmar antes de investir esforço de migração de API nessas telas.
- Target `architect.test` (Karma) em `angular.json` aponta para `karma.conf.js` inexistente — inconsistência preexistente que pode gerar erro em algum schematic do `ng update`.
