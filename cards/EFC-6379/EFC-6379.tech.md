# Plano Técnico — EFC-6379

> Gerado em: 2026-06-02

## Contexto

O módulo `NecessidadesEducacionaisEspeciais` do repositório `notas` recebe 4 melhorias independentes agrupadas nesta epic. A infraestrutura de banco (novos campos + nova entidade `TipoTranstorno`) precisa existir antes das stories de formulário (EFC-6381, EFC-6382). As demais stories são independentes entre si.

**Achado importante:** o campo "possui laudo" pedido no EFC-6381 **não existe ainda** — o campo `PossuiRelatorio` (bool) é diferente (refere-se a relatório pedagógico). O campo `tipoTranstorno` também **não existe** — hoje há apenas `Diagnostico` (string livre). Os campos de mediação igualmente inexistem.

---

## Convenções aplicáveis

1. Entidades herdam de `StatefulEntity`, todas as propriedades `virtual`, sem auditoria declarada.
2. Repositórios herdam de `Repository<T>`, primary constructor C# 12, usam `QueryableAtivos()`.
3. Serviços retornam `ServiceResult<T>`, validação privada antes da lógica.
4. Controllers com `[RequiredAuthorization]`, sem lógica de negócio.
5. Banco via **scripts SQL manuais** — sem EF Core Migrations. Scripts gerados em `cards/EFC-6379/sql/`.
6. Frontend: componentes em `src/app/pages/necessidades-educacionais-especiais/`, modelos em `src/app/models/`, serviço HTTP em `src/app/services/`.

## Critérios de Aceite

### EFC-6380 — Upload de Laudos
- CA-01: Aceitar upload de laudos além do limite atual (novo limite definido após investigação técnica).
- CA-02: Exibir mensagem de erro clara com o limite máximo quando o arquivo for rejeitado.
- CA-03: Upload concluído sem truncamento ou corrupção para laudos com múltiplas páginas.
- CA-04: Laudo disponível para consulta após upload bem-sucedido.

### EFC-6381 — Tipação de Transtorno
- CA-01: Campo "possui laudo" com 3 opções: sim, não, em avaliação.
- CA-02: Campo "tipo de transtorno" como lista suspensa de CIDs com opção "outros" ao final.
- CA-03: Lista de CIDs mantida em entidade própria (importável/gerenciável).
- CA-04: Consultas e exportações funcionam para registros legados (texto livre) e novos (opção selecionada).

### EFC-6382 — Mediação do Aluno
- CA-01: Campo de tipo de mediação: mediação exclusiva, mediação compartilhada, sem mediador.
- CA-02: Campo de texto para nome do mediador.
- CA-03: Filtro de NEE com opção "avaliação mediada".

### EFC-6384 — Relatórios
- CA-01: Relatório exibe apenas alunos com registro NEE ativo no ano letivo corrente.
- CA-02: Distinção clara entre matrícula ativa NEE e histórico.

## Restrições e Riscos

- **Scripts SQL em `cards/EFC-6379/sql/`:** todos os novos campos são `nullable` — sem risco em produção. Cada script deve ter bloco de rollback (`DROP COLUMN` / `DROP TABLE`). Seed de CIDs deve ter script de limpeza correspondente.
- **Retrocompatibilidade `Diagnostico`:** manter o campo existente; novos registros podem usar `TipoTranstorno` ou texto livre ("outros"). Consultas de exportação precisam tratar ambos os formatos.
- **Validação de tamanho no backend:** hoje não existe — qualquer arquivo chega ao S3. Implementar na Fase 2 antes de ir a produção.
- **Relatório EFC-6384:** confirmar semântica de `AlunoEscola.Ativo` com a equipe — a condição `AnLe.Vigente = 1` já existe, mas falta filtro de aluno ativo na matrícula.
- **Lista de CIDs:** definir fonte (CID-10 ou CID-11) e volume antes de criar o seed — pode ser volumoso.
