# EFC-7018 — Como o Painel do Aluno antigo (portal-atlas) obtinha "Aprovado pelo Conselho"

## Resumo

No sistema legado (`portal-atlas`), a informação "Aprovado pelo Conselho" era um **campo pronto** vindo direto de uma view do SQL Server (`dbo.ViewAlunoParaPainel`), sem nenhuma lógica de cálculo no código C#/Knockout — o front só exibia o booleano. Toda a lógica de cálculo fica no banco (na própria view) e, a montante dela, em serviços do `processador-boletim` que alimentam a tabela `AlunoConselhoClasse`.

## 2. Origem do dado no banco (`ElevaPortalHomolog`)

- **`dbo.ViewAlunoParaPainel`** — view SQL Server que contém a coluna `AprovadoPeloConselho` (bit), já pronta por linha (uma linha = um aluno em uma matrícula/ano letivo, via `IdAlunoEscola`/`IdAnoLetivo`/`IdSerie`).
  - **Não foi possível ler a definição da view** — `OBJECT_DEFINITION` e `sys.sql_modules.definition` retornaram `NULL` para o usuário `mcp.readonly` (sem permissão `VIEW DEFINITION`, ou texto protegido). Para ver a lógica exata de cálculo, é preciso pedir a alguém com mais permissão ou abrir via SSMS com um usuário com `VIEW DEFINITION`.
  - **Confirmado que tem dado real em homolog**: `COUNT(*) = 1.195.100` linhas no total, `108.743` com `AprovadoPeloConselho = 1`.
  - Exemplo de linha populada mostra que a view é **por ano letivo** (`IdAnoLetivo` no exemplo = 2020), ou seja, dá para buscar o valor de um ano letivo anterior específico para um aluno (`IdAluno`/`HashAluno` + `IdAnoLetivo`/`IdSerie`).

- **`dbo.AlunoConselhoClasse`** (schema `dbo`, via db_map): colunas `Id`, FK `Avaliacao`, FK `Pessoa`, `DeveSerAplicado`, `TotalComAprovacaoDoConselho`. É granular por **avaliação/disciplina**, não o resumo anual mostrado no painel.

- **`HistoricoSerie`** — existe **duas versões distintas**, não confundir:
  - View `dbo.HistoricoSerie` no SQL Server `ElevaPortalHomolog` — **não encontrada** via `sys.views` com schema `dbo` (a que existe está em `ModuloDocumentacaoPedagogica.HistoricoSerie`, cópia de sincronização, conforme já documentado em `repository_map.md`: 10 colunas, sem dado operacional completo).
  - Tabela `HistoricoSerie` real com `AprovadoPeloConselho`, `Aprovado`, `Reprovado`, `Dependencia`, `MinimoParaAprovacao` — vive no **PostgreSQL próprio do `documentacao-pedagogica`** (banco separado, não é o `ElevaPortalHomolog`).
  - **Nenhuma referência a `HistoricoSerie` foi encontrada no código de `portal-atlas` nem `processador-boletim`** — ou seja, o painel antigo não lia essa tabela diretamente; ele lia a `ViewAlunoParaPainel`, que por sua vez provavelmente é alimentada (via sync/ETL) a partir do resultado final calculado em `documentacao-pedagogica`/`processador-boletim`.

- **`processador-boletim`** (upstream do cálculo, não do painel):
  - `backend\ProcessadorBoletim.Domain.Services\ProcessamentoBoletim\AplicarConselhoClasseService.cs:16` `Calcular(...)` — decide, por disciplina/bimestre, se o conselho se aplica e qual nota atribuir, com base em faixas de `ConselhoClasseDTO` (`DesempenhoMinimo/Maximo`, `RecebeNota`).
  - `backend\ProcessadorBoletim.Domain.Services\AlunoConselhoClasse\AlunoConselhoClasseService.cs:28` `Salvar(...)` — persiste `DeveSerAplicado`/`TotalComAprovacaoDoConselho` na tabela `AlunoConselhoClasse`.
  - Essa camada calcula aprovação **por avaliação/disciplina**, não o resumo anual "aprovado pelo conselho" — a agregação final parece acontecer só na camada de views/sync (fora do controle de versão dos dois repositórios).

## 3. O que isso significa para a implementação em `estrutura-pedagogica`

1. O dado "Aprovado pelo Conselho" **sempre existiu pronto numa view** (`ViewAlunoParaPainel`), nunca foi calculado no backend do painel. A view provavelmente já existe e continua populada em produção (confirmado em homolog) — não é necessário recalcular nada do zero.
2. Para reexibir no novo Painel do Aluno, o caminho mais direto é: identificar se o backend atual do painel em `estrutura-pedagogica` já consulta `ViewAlunoParaPainel` (ou uma view equivalente/nova) para os demais campos do aluno — se sim, basta adicionar `AprovadoPeloConselho` ao DTO/projeção e no frontend Angular. Se o backend novo usa outra fonte (ex.: consulta direta a tabelas em vez da view legada), será preciso decidir se reaproveita `ViewAlunoParaPainel` ou replica a lógica dela.
3. Como não consegui ler a definição da view, **não sei exatamente** se ela calcula o campo olhando o ano letivo **anterior** ao vigente, ou o ano letivo da própria linha. Pelo exemplo de dado puxado, a view parece ser "uma linha por ano letivo" — então para mostrar "aprovado por conselho no ano anterior" no painel do aluno atual, a consulta provavelmente precisa buscar explicitamente a linha do `AnoLetivo - 1` para o aluno, e não apenas o ano vigente.
4. Próximo passo recomendado: pedir a alguém com permissão de `VIEW DEFINITION` (ou abrir via SSMS) a definição de `dbo.ViewAlunoParaPainel` para confirmar a lógica exata e replicá-la (ou simplesmente reconsultá-la) na nova stack.

## 5. Caminhos possíveis para trazer o dado de volta

**Opção A — coluna pré-calculada local (consistente com o padrão atual do repo, recomendado):**
Tratar `AprovadoPeloConselho` como os demais indicadores (`PercentualFrequencia`, `TotalAtendimentos` etc.): nova coluna anulável em `AlunoEscola` (entidade + tabela), incluir no `Select` de `GetParaPainelAluno` (linha 589), no `AlunoPainelAlunoParcialDTO`, no `FormatarResponse`, no `PainelAlunoResponseDTO` e na interface TS.
Risco/trabalho principal: identificar (ou criar) o processo externo que hoje popula os outros indicadores pré-calculados e estendê-lo para também gravar este campo — provavelmente envolve sync/ETL entre `ElevaPortalHomolog`/`processador-boletim` e a base local de `estrutura-pedagogica`.

**Opção B — join direto contra a view legada (mais rápido, mas desvio do padrão arquitetural):**
Fazer uma consulta (ADO/`FromSqlRaw`) contra `dbo.ViewAlunoParaPainel` em `ElevaPortalHomolog`, por `IdAlunoEscola`/`HashAlunoEscola`, e mesclar o resultado dentro de `ListagemPainelAlunoService.Get` — mesmo padrão já usado ali para mesclar `neePorPessoa`/`comportamentosPorPessoaTurma` (linhas 43-51).
Risco: introduz dependência cross-database (hoje o backend só lê sua própria base) e depende de resolver a permissão `VIEW DEFINITION`/leitura na view (o usuário `mcp.readonly` não tem acesso — não sei se a connection string de produção do `estrutura-pedagogica` tem mais permissão).

**Observação importante:** como a `ViewAlunoParaPainel` parece ser "uma linha por ano letivo" (ver seção 2), em qualquer uma das duas opções é preciso buscar explicitamente a linha do **ano letivo anterior** ao vigente para o aluno — não o ano letivo atual.

## 6. Script real da view (fornecido pelo usuário via SSMS) — lógica exata confirmada

O usuário conseguiu extrair o script `ALTER VIEW [dbo].[ViewAlunoParaPainel]` direto do SSMS (com permissão que o `mcp.readonly` não tem). O trecho relevante:

```sql
-- Aprovado pelo Conselho
LEFT JOIN (SELECT DISTINCT AlCo.Pessoa, TiAv.AnoLetivo, 1 AS Aprovado

           FROM       AlunoConselhoClasse AS AlCo
           INNER JOIN Avaliacao           AS Av   ON Av.Id = AlCo.Avaliacao
           INNER JOIN TipoAvaliacao       AS TiAv ON TiAv.Id = Av.TipoAvaliacao

           WHERE AlCo.DeveSerAplicado = 1
             AND AlCo.Ativo = 1

          ) AS AprovadoPeloConselho ON AprovadoPeloConselho.Pessoa    = Pe.Id
                                   AND AprovadoPeloConselho.AnoLetivo = (EsSe.Anoletivo - 1)
...
IsNull(AprovadoPeloConselho.Aprovado, 0) AS AprovadoPeloConselho,
```

**Lógica exata, confirmada (não é mais hipótese):**

> Um aluno é "Aprovado pelo Conselho" (no contexto de uma linha da view cujo ano letivo é `EsSe.AnoLetivo`) se existir **pelo menos uma** linha em `AlunoConselhoClasse` para essa `Pessoa`, ligada via `Avaliacao → TipoAvaliacao`, cujo `TipoAvaliacao.AnoLetivo = EsSe.AnoLetivo - 1`, com `AlunoConselhoClasse.DeveSerAplicado = 1` e `AlunoConselhoClasse.Ativo = 1`. Caso contrário, `0`.

Isso **confirma e simplifica** o que a seção 2/5 só suspeitava:
- Minha suposição inicial de que seria preciso "buscar a linha do ano letivo anterior" estava certa, mas o mecanismo é simples: não há agregação complexa nem `TotalComAprovacaoDoConselho` envolvido — só um `EXISTS`/`DISTINCT` em `AlunoConselhoClasse.DeveSerAplicado = 1 AND Ativo = 1`, filtrado por `AnoLetivo = AnoLetivoAtual - 1`.
- `Avaliacao` e `TipoAvaliacao` são só pontes para chegar ao `AnoLetivo` — a tabela de fato é só `AlunoConselhoClasse`.

### Isso muda a recomendação da seção 5

Como [[project_db_compartilhado_portal_atlas_estrutura_pedagogica]] confirma que `portal-atlas` e `estrutura-pedagogica` **leem a mesma base física** (não é cross-database), a Opção B deixa de ser um "desvio arquitetural com dependência externa" — `AlunoConselhoClasse`, `Avaliacao` e `TipoAvaliacao` são tabelas **na mesma conexão/base** que o `estrutura-pedagogica` já usa para tudo o mais (`AlunoEscola`, `Pessoa`, etc.).

**Recomendação revisada:** replicar essa lógica como uma consulta EF Core LINQ adicional (ou mapear as 3 tabelas como entidades, se ainda não existirem no `DbContext` do `estrutura-pedagogica`) dentro de `ListagemPainelAlunoService.Get` — no mesmo padrão em que hoje já se mesclam `neePorPessoa`/`comportamentosPorPessoaTurma` (linhas 43-51 de `ListagemPainelAlunoService.cs`):

1. Buscar, para o conjunto de `Pessoa.Id` retornado por `GetParaPainelAluno`, se existe `AlunoConselhoClasse` com `DeveSerAplicado = 1 AND Ativo = 1` cujo `Avaliacao.TipoAvaliacao.AnoLetivo = EsSe.AnoLetivo - 1` (o ano letivo da matrícula atual do aluno, não um valor fixo).
2. Montar um `HashSet<int>`/dicionário `Pessoa → bool` (como já é feito para NEE/comportamento).
3. Preencher `aprovadoPeloConselho` no `FormatarResponse`, no `PainelAlunoResponseDTO` e na interface Angular `PainelAlunoResponse`.

Isso elimina a necessidade de nova coluna pré-calculada (Opção A) ou de acesso cross-database (Opção B original) — é só mais um `LEFT JOIN`/consulta auxiliar igual às que já existem no service, usando tabelas que já estão na mesma base.

**Verificado (2026-10-09):**
