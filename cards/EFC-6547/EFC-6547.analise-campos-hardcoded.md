# Análise — campos "hardcoded" na aba Anamnese (não vêm do endpoint)

> **Isto é uma análise, não um plano de execução.** Levantamento do que hoje é lógica/dado fixo no
> frontend (`AnamneseTabComponent`/`PerguntaRepetivelComponent`/`anamnese-widgets.util.ts`) versus o
> que realmente vem do endpoint `getanamnese` (`PerguntaAnamneseResponse`, ver
> `frontend/src/app/features/painel-aluno/models/models.ts`). Nenhuma mudança de código foi feita.

## Contexto

O `data.json` (payload real do endpoint) só carrega, por pergunta: `hash, texto, tipoResposta,
obrigatoria, condicional, multiplaSelecaoResposta, hashOpcaoGatilho, ordem, repetivel,
hashPerguntaAgrupadora, opcoes[], ehIrmaoNaRede, irmaosIdentificados[]` + os campos de resposta.
Ele **não manda**: qual componente/widget usar, rótulos de opções fixas (Sim/Não, Masculino/
Feminino), limiares de UI (quando virar dropdown), nem nada sobre "irmãos identificados" além da
lista de nomes. Toda essa decisão de apresentação está hardcoded no frontend, replicada em pelo
menos 2 lugares (`AnamneseTabComponent` e `PerguntaRepetivelComponent`) — e um terceiro
(`anamnese-form-mapper.ts`, demo do `form-section-builder`).

## O que é hardcoded, por tipo de pergunta

| `TipoRespostaAnamneseEnum` | O que vem do endpoint | O que é fixo no frontend |
|---|---|---|
| `SimNao` (1) | só o `tipoResposta` | rótulos "Sim"/"Não" e hashes `'sim'/'nao'` — `OPCOES_BINARIO` (`anamnese-tab.component.ts:49`, duplicado em `pergunta-repetivel.component.ts:76`) |
| `Sexo` (2) | só o `tipoResposta` (zero `opcoes`) | rótulos "Masculino"/"Feminino" + códigos numéricos 1/2 — `OPCOES_SEXO` (`anamnese-widgets.util.ts:30-33`) e a decisão de usar `respostaNumerica` em vez de `hashesOpcoesSelecionadas` (`ehSexo()`, linha 65-67) |
| `Inteiro` (3) | só o `tipoResposta` | branch dedicado fora dos utils — `text-field` com placeholder `'Número'` hardcoded (`anamnese-tab.component.html:78-83`); sem máscara/validação de número |
| `Data` (4) | só o `tipoResposta` | branch dedicado — sempre `app-date-field`, sem opção de outro formato (`anamnese-tab.component.html:85-89`) |
| `Mascara` (5) | só o `tipoResposta` | agrupado em `TIPOS_TEXTO_SIMPLES` — cai num `text-field` genérico; a "máscara" em si nunca é aplicada (comentário explícito: "fora de escopo desta fase") |
| `ListaOpcoes` (6) | `opcoes[]` (hash+nome) + `multiplaSelecaoResposta` | **o limiar radio-vs-dropdown** (`LIMITE_OPCOES_RADIO = 8`, `anamnese-widgets.util.ts:40`) é um número fixo, não configurável por pergunta |
| `TextoAberto` (7) | só o `tipoResposta` | agrupado em `TIPOS_TEXTO_SIMPLES` — placeholder fixo `'Resposta'` |
| `Telefone` (8) | só o `tipoResposta` | agrupado em `TIPOS_TEXTO_SIMPLES` — vira `text-field` genérico, sem máscara de telefone |
| `TextoLongo` (9) | só o `tipoResposta` | branch dedicado fora dos utils — sempre `app-textarea-field` (`anamnese-tab.component.html:72-76`) |
| `Celular` (10) | só o `tipoResposta` | mesmo caso de Telefone — texto simples sem máscara |
| `AlunoComMesmoResponsavel` (11) | só o `tipoResposta` (+ `ehIrmaoNaRede`/`irmaosIdentificados` quando aplicável) | **stub**: `OPCOES_ALUNO_MESMO_RESPONSAVEL = []` hardcoded vazio, renderiza um `app-select-field` com placeholder `'Seleção de aluno — funcionalidade pendente'` (`anamnese-tab.component.ts:54`, `anamnese-tab.component.html:224-232`) — não existe componente de "seleção de aluno" no design system, então esse tipo **não é funcional hoje** |
| `DisciplinasAluno` (12) | só o `tipoResposta` | a lista de opções **não vem do endpoint de Anamnese** — é buscada de um endpoint separado, `PainelAlunoService.getDisciplinasAtendimento` (reaproveitado do Norteador de Atendimento) — `anamnese-tab.component.ts:511-531`; inclui um mecanismo de "pendente" (`marcarPendente`/`limparPendenciaDisciplinas`) só para essa requisição assíncrona |

## Regras de negócio hardcoded que não são "por tipo", mas por flag/heurística

- **`ehIrmaoNaRede` força dropdown, ignorando `LIMITE_OPCOES_RADIO`** — mesmo que a pergunta tenha
  poucas opções, o frontend decide sempre usar `app-select-field` (`ehSelecaoUnicaDropdown`,
  `anamnese-widgets.util.ts:78-81`). A flag `ehIrmaoNaRede` vem do endpoint (via
  `TipoPerguntaAnamnese.Id=1`), mas a **regra de exibição** em si (forçar dropdown) é hardcoded.
- **Filtro de opções mínimas do "Irmão(ã) na Rede"** (`opcoesParaDropdown`/`valorNumericoDaOpcao`,
  `anamnese-tab.component.ts:220-240`) — faz `regex /\d+/` sobre o **texto livre** da opção (ex.:
  `"2 irmãos(ãs)"` → `2`) pra descartar opções abaixo da quantidade de irmãos identificados
  automaticamente. Isso é uma extração de número do texto da opção, sem nenhum dado estruturado do
  backend pra apoiar — se o texto de uma opção mudar no cadastro (ex.: "2 irmãos" sem "(ãs)"), a
  regra pode silenciosamente parar de filtrar corretamente.
- **Lista somente-leitura de "Irmão(s) identificado(s) automaticamente"** — todo o bloco
  (`anamnese-tab.component.html:170-191`, ícone `person` + `"{{nome}} — {{turma}}"`) é uma UI
  bespoke atrelada especificamente a essa pergunta, fora do fluxo genérico de widgets.

## O que **não** é hardcoded (contraponto — já é genérico/dirigido por dados)

- **Visibilidade condicional** (`perguntaVisivel`, `Condicional` + `HashOpcaoGatilho`) — funciona
  para qualquer pergunta que tenha esses campos preenchidos, sem checar hash/tipo específico.
- **Cadeia de pergunta repetível** (`repetivel` + `hashPerguntaAgrupadora`, `cadeiaDaPergunta`) —
  também genérico: funciona pra qualquer profundidade/composição de cadeia, não hardcoded para
  "Outro(a) Irmão(ã)" ou "Especialidade" especificamente.
- Isso mostra que a arquitetura já tem DOIS mecanismos genéricos reais (condicional e cadeia) — o
  hardcode está concentrado na camada de **escolha/config de widget por tipo**, não na estrutura
  de dados em si.

## Relação com a análise anterior (`form-section-builder`)

Esse levantamento reforça exatamente o ponto já registrado em
`EFC-6547.analise-blocos-injetaveis.md`: a resolução de widget por `*ngIf`/tipo é o que gera tanto
a duplicação entre `AnamneseTabComponent`/`PerguntaRepetivelComponent` quanto os pontos hardcoded
listados acima. Um motor tipo `form-section-builder` não elimina o hardcode em si (alguém ainda
precisa decidir "SimNao → radio com Sim/Não", "Sexo → radio com Masculino/Feminino 1/2" etc.), mas
**centraliza essa decisão em UM mapeador** (equivalente ao `anamnese-form-mapper.ts` da demo) em vez
de duplicá-la em 2-3 lugares — e deixa mais visível/isolado o que é regra de negócio genuína (ex.:
filtro de irmãos, força-dropdown do Irmão-na-Rede) versus o que é só "widget padrão para este tipo".

O caso do `AlunoComMesmoResponsavel` (stub vazio, não funcional) e do `DisciplinasAluno`
(dependência de outro endpoint) seguem sendo os dois pontos mais delicados: nenhum motor genérico
resolve isso por si só — ainda vai exigir, respectivamente, um componente de seleção de aluno (hoje
inexistente no design system) e uma forma de o `FieldConfig`/mapeador carregar opções assíncronas de
uma fonte externa à config declarativa.
