# Análise — Anamnese como sistema de blocos injetáveis (comparação com Filtro e Document-Builder)

> Análise, não plano de execução — nenhuma mudança de código foi feita a partir daqui. Espaço para o usuário adicionar ideias/considerações.

## Contexto

Durante a implementação da aba Anamnese (EFC-6547), a resolução de "qual widget renderizar para cada pergunta" foi feita via uma cadeia de `*ngIf` sobre flags booleanas (`ehTextoSimples`, `ehSexo`, `ehRadioBinario`, `ehSelecaoUnicaRadio`, `ehSelecaoUnicaDropdown`, `ehSelecaoMultiplaOpcoes`, mais casos especiais como `ehIrmaoNaRede`), com a lógica de decisão extraída para um util compartilhado (`anamnese-widgets.util.ts`), mas o **HTML de cada widget duplicado em dois lugares**: `anamnese-tab.component.html` (perguntas normais) e `pergunta-repetivel.component.html` (perguntas dentro de uma cadeia repetível). O bug do "Sexo" (campo não renderizava) precisou ser corrigido nos dois templates porque a marcação do widget em si — não só a decisão de qual usar — está duplicada.

O usuário observou que dois outros sistemas do mesmo repositório (`filtro` e `document-builder`, cada um com README próprio) já resolvem "montagem de formulário/documento a partir de blocos configuráveis" de um jeito mais programático, e pediu uma análise se algo parecido faria sentido para a Anamnese.

## O que os dois sistemas existentes fazem

### `shared/filtro/` (`frontend/src/shared/filtro/README.md`)

- Um filtro é **dados**: `FilterConfig` com um array `FilterItemConfig[]` (campo, tipo, cascata de dependências, fonte de opções).
- Resolução do widget é **injeção real de componente Angular em runtime**: `component.map.ts` é um `Record<FieldType, Type<Component>>`; `FiltroComponent` faz `ViewContainerRef.createComponent(FilterFieldWrapperComponent)`, que por sua vez cria o widget concreto via `ViewContainerRef.createComponent(componentType, { injector })`, com um `Injector` customizado (`DynamicInjectorService`) que registra `FormControl`, `options`, `key` etc. como providers — o widget recebe tudo via `@Inject(...)` no construtor, não só `@Input()`.
- Estado é Reactive Forms — um `FormGroup` por filtro, cacheado por `config.id` em `FiltroFormService`.
- Adicionar um tipo de campo novo = criar o componente + adicionar 1 linha em `component.map.ts` + 1 valor no enum `FieldType`. Não toca `filtro.component.ts`/`field-wrapper.component.ts` (agnósticos ao tipo).

### `shared/document-builder/` (`frontend/src/shared/document-builder/README.md`)

- Um bloco é **dados**: `DocumentEntry<T>` = `{ data: T, componentType: Type<{data: T}> }` — o "tipo" é literalmente a classe do componente, não um enum.
- Resolução também é `ViewContainerRef.createComponent(entry.componentType)`, com `reflectComponentType()` pra descobrir quais `@Input()`s o componente aceita antes de setar (`ref.setInput(...)`), e o `nativeElement` é anexado manualmente ao DOM.
- Esse mecanismo existe porque o `DocumentViewer` precisa **medir a altura renderizada de cada bloco antes de decidir a paginação** — não dá pra saber isso em tempo de template estático. Não é um "estilo preferido", é uma necessidade do problema (paginação).
- Não há mapa central de tipo→componente — cada `DocumentEntry` já carrega a classe.

## Comparação com a Anamnese hoje

| | Filtro | Document-builder | Anamnese (atual) |
|---|---|---|---|
| Widget é... | resolvido por mapa `FieldType→Type` | a própria classe embutida no dado | resolvido por `*ngIf` sobre flags no template |
| Estado | Reactive Forms, `FormGroup` central | N/A (documento é read-only na exibição) | Reactive Forms, mas sem `formControlName` (por causa do `ng-template` do accordion) — controles soltos, bind manual |
| Motivo da injeção dinâmica | generalidade + extensibilidade | necessidade de medir altura pra paginar | (não existe hoje — é tudo estático) |
| Duplicação de widget | nenhuma — 1 componente, 1 lugar | nenhuma — 1 componente, 1 lugar | **sim** — cada tipo aparece em 2 templates (aba normal + pergunta repetível) |

## Isso faz sentido pra Anamnese?

**Sim, arquitetonicamente — e o precedente certo é o `filtro`, não o `document-builder`.** O `document-builder` resolve um problema que a Anamnese não tem (paginação/medição); replicar aquele mecanismo específico (criação manual de `nativeElement`, `reflectComponentType`) seria over-engineering. Já o padrão do `filtro` — config de campo (dado) + mapa tipo→componente + injeção via `ViewContainerRef.createComponent`/`Injector` + `FormGroup` central — é estruturalmente muito parecido com o que a Anamnese precisa: N perguntas, cada uma com um tipo, cada uma virando um widget.

**Ganho concreto já observado nesta sessão:** o bug do "Sexo" exigiu editar dois templates porque a Anamnese tem dois "consumidores" de pergunta (a aba normal e o componente de pergunta repetível), e cada widget está com sua marcação duplicada entre eles. Um resolvedor de bloco único (map + injeção, ao estilo `filtro`) usado pelos dois consumidores eliminaria essa duplicação — um novo tipo de widget (ou correção de um existente) passaria a ser tocado em um lugar só.

**O que esse refactor NÃO resolveria:** a lógica de negócio específica da Anamnese (cadeias de pergunta repetível com N instâncias, visibilidade condicional via `hashOpcaoGatilho`, a lista de irmãos identificados automaticamente, o filtro de "quantidade mínima selecionável") é ortogonal à resolução de widget — ela ficaria em uma camada acima do resolvedor de bloco, do mesmo jeito que hoje. Não seria "adotar o padrão do filtro" que simplifica essa parte; ela continuaria bespoke.

**Custo:** é um refactor de porte real — envolveria embrulhar cada widget atual (`text-field`, `app-select-field`, `app-date-field`, radio/checkbox nativos, Sexo, disciplinas, aluno-mesmo-responsável) num componente com contrato comum (`@Input() control` + o que mais for necessário via `@Inject`), criar um `component.map.ts`-equivalente para Anamnese, e um wrapper único consumido tanto por `anamnese-tab.component` quanto por `pergunta-repetivel.component`. Como a aba já está funcionalmente quase completa (várias rodadas de correção pontual já aplicadas), isso é mais bem enquadrado como um **refactor de acompanhamento**, não um pré-requisito para terminar o que falta (E2E, "Irmão na Rede"/`AlunoComMesmoResponsavel`, campos repetíveis com mais de 2 níveis).

## Recomendação (da IA)

Vale a pena fazer — mas depois, não agora, e com escopo próprio (provavelmente um novo card/tarefa dedicado, não um adendo ao EFC-6547). Antes de decidir quando, os dois pontos ainda abertos do card (comportamento de "Irmão na Rede" com `AlunoComMesmoResponsavel`, e a pergunta ainda em aberto sobre isso) valem ser resolvidos primeiro — refatorar a resolução de widget enquanto a modelagem de dados de alguns campos ainda está em aberto arriscaria ter que revisitar o resolvedor de novo em seguida.

## Refinamento da proposta (IA)

A proposta se sustenta e é mais elegante que o meu esboço inicial — em particular, tratar pergunta repetível como "grupo dentro de grupo" (em vez de um componente especial só para isso) resolve de raiz a duplicação de template que motivou essa discussão. Abaixo, o desenho concreto e os pontos que precisam de decisão antes de implementar.

### Nome

**Decidido: `form-section-builder`.**

Local: `frontend/src/shared/form-section-builder/`, com README próprio (mesmo padrão de `filtro`/`document-builder`).

### Separação genérico vs. específico da Anamnese (ponto crítico)

O componente genérico **não pode receber o DTO do `getanamnese` diretamente** — isso o prenderia para sempre aos nomes de campo da Anamnese (`awesomeIcon`, `tipoResposta`, `hashPerguntaAgrupadora` etc.), contradizendo o próprio objetivo de reuso futuro. O padrão certo (o mesmo que `filtro` já usa) é:

```
AnamneseResponse (DTO, sem mudança)
        │
        ▼
  mapeador específico da Anamnese          ← só esta parte conhece "Anamnese"
  (ex.: anamnese-form.mapper.ts, dentro
   de features/painel-aluno, NÃO em shared/)
        │
        ▼
  GroupConfig[] / FieldConfig[]             ← modelo genérico (shared/form-section-builder/form-section-builder.models.ts)
        │
        ▼
  <app-form-section-builder [grupos]="config">  ← genérico, nunca soube o que é "Irmão(ã) na Rede"
```

Isso espelha exatamente `filtro`: `configFiltroPainelAluno()` (específico) monta `FilterConfig` (genérico) que `FiltroComponent` (genérico) consome. Sem esse mapeador intermediário, "genérico" seria só um nome — o componente ainda estaria acoplado à Anamnese.

O mapeador é também o lugar certo para decidir *qual* widget cada pergunta usa — isto é, toda a lógica que hoje está em `anamnese-widgets.util.ts` (`ehSexo`, `ehRadioBinario`, `ehSelecaoUnicaRadio` vs. `ehSelecaoUnicaDropdown` por contagem de opções) migra para dentro do mapeador, decidindo um `FieldType` genérico (`radio-fixo`, `radio-opcoes`, `select-opcoes`, `checkbox-opcoes`, `texto`, `numero`, `data`, `grupo-repetivel`, ...) por pergunta. O `form-section-builder` genérico só conhece esse vocabulário de `FieldType`, nunca `TipoRespostaAnamneseEnum`.

### Grupos dentro de grupos (pergunta repetível generalizada)

Um `FieldConfig` de tipo `grupo-repetivel` carrega seus próprios `subItens: FieldConfig[]` (a cadeia — hoje "Outro(a) Irmão(ã) → Sexo → Nascimento"). O componente que renderiza esse tipo (`RepeatableGroupFieldComponent`, novo, em `dynamic-components/`) gerencia N instâncias + "+"/remover, e para cada instância **chama de volta o próprio motor genérico** para renderizar `subItens` — recursivo, então funciona igual para a cadeia de 2 níveis ("Irmão") e a de 5 níveis ("Especialista") sem código particular para cada uma. Isso elimina o `PerguntaRepetivelComponent` como componente *especial* — ele passa a ser só mais uma entrada no mapa de tipo→componente, e some a duplicação entre `anamnese-tab.component.html`/`pergunta-repetivel.component.html` (só existe um caminho de renderização).

O "grupo" no nível de fora (o accordion — Família, Hobbies, etc.) é o mesmo mecanismo em um nível acima: `GroupConfig[]` com `itens: FieldConfig[]`, onde cada `FieldConfig` pode por sua vez ser um `grupo-repetivel`. Ou seja, accordion-de-seções e grupo-repetível-de-instâncias são a mesma estrutura recursiva aplicada em dois níveis — vale desenhar como *um* conceito (`GroupConfig`/`FieldConfig` recursivos), não dois.

O `AnamneseAccordionComponent` (já existe, T6) é candidato a ser generalizado e promovido para dentro do `form-section-builder` como o container de `GroupConfig` — hoje ele já é bem próximo de agnóstico (só sabe de `hash/nome/awesomeIcon/ordem` + conteúdo projetado).

### Resolução de componente — sem mapa fechado, seguindo o `document-builder`

**Achado que muda o desenho anterior desta análise:** o `document-builder` já resolve exatamente o requisito de extensibilidade que motivou a pendência do "Irmão(ã) na Rede" — e de um jeito mais simples do que o "mapa + extensão" que eu tinha esboçado. Confirmado em `shared/document-builder/models/layout.models.ts:91-95`:

```typescript
// The public API for declaring document content.
// Developers provide this list; DocumentViewer handles instantiation and measurement.
export interface DocumentEntry<T = unknown> {
  data: T
  componentType: Type<{ data: T }>   // a própria classe do componente, não um enum/string
  name?: string
}
```

**Não existe mapa/registro nenhum no `document-builder`.** Cada entrada já carrega a classe do componente Angular diretamente; o motor genérico só faz `ViewContainerRef.createComponent(entry.componentType)` e depois `ref.setInput(...)` (com `reflectComponentType()` pra descobrir quais inputs o componente aceita).

**Proposta revisada para o `form-section-builder`, herdando esse padrão:** `FieldConfig` carrega `componentType: Type<{ control: FormControl, ... }>` diretamente — a classe, não uma string de tipo. O mapeador da Anamnese (não o motor genérico) decide, pergunta a pergunta, qual classe usar: para os tipos comuns, referencia os componentes de `dynamic-components/` (`text-field`, `app-select-field`, `app-radio-field`, `app-date-field`, ...); para "Irmão(ã) na Rede", referencia um componente próprio da Anamnese (fora de `dynamic-components/`). **Do ponto de vista do motor genérico não há diferença entre os dois casos** — ele nunca precisa conhecer nem um mapa de tipos nem uma lista de exceções, só recebe a classe já resolvida. Isso elimina de vez a necessidade de qualquer `@Input() mapaAdicional`/mecanismo de extensão — o "componente que ele não conhece" já é suportado nativamente, do mesmo jeito que qualquer outro.

`FieldType` (string) pode continuar existindo no `FieldConfig` como metadado (útil pro mapeador decidir validadores, ou pra debug), mas deixa de ser a chave de resolução do widget — quem resolve é `componentType`.

Componentes a reaproveitar de `dynamic-components/`: `text-field`, `app-select-field`, `app-multi-select-field`, `app-date-field`, `app-textarea-field`, e o que **já existe mas não foi usado por decisão de prazo** — `app-radio-field` (`shared/dynamic-components/radio-field/`), que faz exatamente o que os radios manuais da Anamnese fazem hoje, só que via `[formControl]` de verdade. A pré-condição para usá-lo é resolver a inconsistência de formato de valor (escalar vs. array) na *origem* (mapeador), não mais via workaround no componente — um dos ganhos colaterais desse refactor.

Vai precisar de pelo menos 1 componente novo em `dynamic-components/`: um **checkbox-group** (hoje é HTML cru na Anamnese, não existe componente pronto para seleção múltipla em checkboxes inline).

### Validação específica da Anamnese

Ponto de extensão necessário — duas camadas, ambas já com precedente em `filtro`:
1. **Por campo**: `FieldConfig` carrega `validators?: ValidatorFn[]` (tipo nativo do Angular) — o mapeador da Anamnese anexa aqui qualquer regra de campo único. Resolve a maioria dos casos.
2. **Entre campos / do grupo**: `filtro` já tem precedente (`dependencyValidator`, que lê outros controles do mesmo `FormGroup`). O `form-section-builder` deveria expor o `FormGroup`/`FormArray` construído (via `@Output()` ou getter) para que o consumidor (Anamnese) anexe validadores cross-field depois de montado, ou aceitar um `@Input() validadoresDoGrupo: ValidatorFn[]` aplicado no `FormGroup` raiz de cada `GroupConfig`.

### O que fica igual (confirmado, sem mudança de backend)

`GetAnamnese`/`SalvarAnamnese`, os DTOs, `AnamneseGetService`/`AnamneseSaveService`, a lógica de cadeia (`AnamnesePessoaResposta`/`AnamnesePessoaRespostaAgrupadaId`) — nada disso muda. O mapeador consome o `AnamneseResponse` exatamente como está hoje; a montagem do payload de save (`RespostaAnamneseRequest[]`, incluindo `instanciaIndice`) também continua uma responsabilidade do lado Anamnese (desmontando o `FormGroup`/`FormArray` genérico de volta), não do motor genérico.

### "Irmão(ã) na Rede" — deixado em aberto por decisão do usuário

Não decidir agora como esse campo (`TipoResposta=AlunoComMesmoResponsavel`, repetível, ver pergunta anterior no card) vai funcionar. Já fica registrado, porém, que com o padrão de resolução por `componentType` (herdado do `document-builder`, ver acima) isso deixa de ser um problema de arquitetura: quando a decisão for tomada, o mapeador da Anamnese só precisa apontar `componentType` para um componente próprio (fora de `dynamic-components/`) nessa pergunta específica — o motor genérico não precisa de nenhum mecanismo especial pra isso, já é o comportamento padrão pra qualquer campo.
