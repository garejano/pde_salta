# Análise — performance e memory leak no `form-section-builder`

> Análise, nenhuma mudança de código foi feita. Escopo: `frontend/src/shared/form-section-builder/`
> (o motor genérico em si — `FormSectionBuilderComponent`, `FieldHostComponent`,
> `RepeatableGroupFieldComponent`, `FormSectionGroupComponent`, `models.ts`). Os widgets consumidos
> (`shared/dynamic-components/*`) e o mapper da demo não foram revisados aqui.

## 🔴 Memory leak confirmado — `RepeatableGroupFieldComponent.removerInstancia()`

`repeatable-group-field.component.ts:120-130`

```ts
removerInstancia(indice: number): void {
  if (this.linhas.length <= 1) { ... }
  else {
    this.linhas = this.linhas.filter((_, i) => i !== indice);
    this.controlesPorLinha = this.controlesPorLinha.filter((_, i) => i !== indice);   // <-- aqui
  }
  this.emitir();
}
```

`controlesPorLinha[indice]` guarda um `Record<string, FormControl>` cujos controles foram criados em
`construirControlesDaLinha()` com `.valueChanges.subscribe(...)` — cada subscription é empurrada pra
`this.subscriptions` (array **plano**, compartilhado entre TODAS as linhas). `removerInstancia()`
descarta a REFERÊNCIA da linha removida (`controlesPorLinha.filter(...)`), mas nunca desinscreve as
subscriptions daqueles controles específicos — elas continuam vivas em `this.subscriptions` até o
componente inteiro ser destruído (`ngOnDestroy`) ou até `sincronizarDoControl()` rodar de novo (só
acontece se `control`/`subItens` mudar de referência por fora, não por `adicionarInstancia`/
`removerInstancia`).

**Efeito prático:** cada ciclo de "adicionar uma linha, preencher, remover" deixa `subItens.length`
`FormControl`s + subscriptions órfãos presos em memória (inalcançáveis pela UI, mas mantidos vivos
pela própria subscription referenciando o `Subject` interno do `FormControl`). Numa sessão longa
onde o usuário adiciona/remove várias vezes (ex.: "Outro(a) Irmão(ã)", "Especialidade"), esse array
cresce sem limite até o componente ser destruído.

**Correção sugerida:** desinscrever as subscriptions da linha ANTES de descartar sua referência —
precisa que `construirControlesDaLinha` devolva também as subscriptions daquela linha (hoje só
`this.subscriptions` no nível do componente sabe quais existem, sem agrupamento por linha), ou
trocar `this.subscriptions: Subscription[]` por `Subscription[][]` (uma lista por linha, no mesmo
índice de `controlesPorLinha`), e desinscrever `subscriptions[indice].forEach(s => s.unsubscribe())`
antes do `.filter()`.

## 🟡 Leak menor — `FormSectionBuilderComponent.visibilidadeAnterior` nunca é limpo

`form-section-builder.component.ts:49`

`donoDeOpcao` é limpo (`recomputarDonoDeOpcao()` chama `.clear()`) toda vez que `repopularFormGroup()`
roda — mas `visibilidadeAnterior` (mesmo propósito: estado por `campo.id`) nunca é. Se o
`FormSectionBuilderComponent` for reaproveitado ao longo da vida da página com `config` trocando
várias vezes (ex.: trocar de aluno/ano letivo mantendo o mesmo `<app-form-section-builder>` na
tela — não é o caso da demo atual, que recria a página inteira, mas é o padrão esperado numa
integração real), esse `Map` acumula uma entrada por `campo.id` já visto, incluindo `campo.id`s de
configs antigas que não existem mais. Baixo impacto absoluto (limitado à quantidade de perguntas
distintas já vistas na sessão, não cresce por interação do usuário), mas é uma inconsistência com o
`donoDeOpcao` do lado, que já limpa corretamente — fácil de alinhar.

## 🟡 Performance — visibilidade condicional recomputada em TODO ciclo de change detection

`form-section-builder.component.html:11` — `*ngIf="campoVisivel(campo)"` chama um método diretamente
no template, pra CADA campo, em CADA ciclo de CD (Angular reavalia expressões de template a cada
tick do zone.js — qualquer evento/timer/XHR em QUALQUER lugar da página, não só dentro deste
formulário, dispara isso, já que nenhum componente do módulo usa `ChangeDetectionStrategy.OnPush`).

Pra cada campo condicional, `campoVisivel()` → `opcaoEstaSelecionada()`/`valorDoCampoIgual()` fazem
`Map.get()` + `FormGroup.get()` (percorre o path) + `hashesSelecionados()` (que aloca um array novo
via `.filter()` a cada chamada). Campos não-condicionais saem cedo (2 checagens booleanas), então o
custo real é proporcional só à quantidade de perguntas condicionais — hoje pequeno (a Anamnese tem
~10 delas), mas o padrão em si ("computar visibilidade via chamada de método no template, sem
cache") não escala bem se o motor for reaproveitado num formulário bem maior.

Interessante notar que a visibilidade já É recomputada de forma "empurrada" (não só "puxada" pelo
template) em `reavaliarVisibilidade()`, disparada por `formGroup.valueChanges` — ou seja, hoje o
motor faz o trabalho de visibilidade **duas vezes** por interação: uma vez via a subscription
(pra decidir se limpa o valor de um campo que acabou de esconder) e outra vez via o template (pra
decidir o que renderizar), sem compartilhar o resultado entre as duas.

**Correção sugerida:** manter um `Set<string>` (ou `Map<string, boolean>`) de "campos visíveis
agora", atualizado uma vez por `reavaliarVisibilidade()` (que já roda a cada `valueChanges`), e o
template ler desse Set em vez de chamar `campoVisivel()` diretamente — uma fonte de verdade só, sem
recomputar em cada CD cycle nem duplicar o trabalho.

## 🟡 Performance — `reflectComponentType()` não é cacheado por classe de componente

`field-host.component.ts:106-109` — toda chamada a `aplicarInputs()` (ou seja, toda vez que
`campo`/`control` mudam de referência) roda `reflectComponentType(campo.componentType)` de novo,
mesmo quando o `componentType` é o mesmo de antes (ex.: só o `control` mudou, caso comum ao trocar
linha de uma cadeia repetível ou repopular a config). O resultado de `reflectComponentType` é
**estático por classe** — os `@Input()`s declarados de `RadioFieldComponent` nunca mudam em
runtime — então recalcular isso por instância, a cada mudança, é trabalho redundante que poderia ser
cacheado uma vez por `componentType`, compartilhado entre TODAS as instâncias de `FieldHostComponent`
da aplicação (ex.: `Map<Type<unknown>, Set<string>>` em escopo de módulo, fora da classe).

## 🟢 Verificado e correto (sem problema encontrado)

- `FieldHostComponent`: subscriptions assíncronas (`assinarPropAssincrona`) são limpas corretamente
  em 3 pontos — início de `aplicarInputs()` (evita acumular se rodar de novo sem trocar tipo), antes
  de `host.clear()` ao trocar `componentType`, e em `ngOnDestroy`. Sem leak aqui.
- `FormSectionBuilderComponent`: a subscription de `valueChanges` é corretamente re-substituída
  (`unsubscribe()` antes de resubscrever) a cada `repopularFormGroup()`, e limpa em `ngOnDestroy`.
- `RepeatableGroupFieldComponent`: `sincronizarDoControl()` limpa TODAS as subscriptions antes de
  reconstruir (correto para o caso de troca de `control`/`subItens` por inteiro) — o leak descrito
  acima é específico do caminho `removerInstancia()`, que não passa por `sincronizarDoControl()`.
- `trackBy` usado corretamente em todo `*ngFor` do módulo (`trackByGrupoId`, `trackByCampoId`,
  `trackByIndex`, `trackByItemId`) — Angular não recria DOM/componentes desnecessariamente.
- Cópias defensivas de array (`[...this.linhas]` em `emitir()`, etc.) são baratas e necessárias
  (mudar referência é o que dispara `OnPush`/CD a perceber a mudança) — não é desperdício.

## Não avaliado (fora do escopo desta rodada)

- `ChangeDetectionStrategy.OnPush` em todo o módulo — mudança estrutural maior (precisa garantir que
  toda interação relevante realmente dispara `markForCheck()`/vem de um Observable com `async` pipe
  ou de uma diretiva reativa compatível); vale uma análise própria se o motor crescer de uso.
- Os widgets em `shared/dynamic-components/*` (radio-field, checkbox-group-field, multi-select-field
  etc.) — usados pelo motor, mas não fazem parte dele; não revisados nesta rodada.
- O mapper da demo (`anamnese-form-mapper.ts` e afins) — não é parte do motor genérico.
