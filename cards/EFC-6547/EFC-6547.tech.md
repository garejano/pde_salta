# Plano Técnico — EFC-6547

> Gerado em: 2026-08-19

## Contexto

A aba Anamnese do Painel do Aluno (`estrutura-pedagogica`) existe hoje só como placeholder no frontend (`anamnese-tab.component.ts/.html` — ícone "em desenvolvimento"). Toda a modelagem de dados (entidades `AnamnesePessoa`, `VersaoAnamnese`, `PerguntaVersaoAnamnese`, `GrupoPerguntaAnamnese` etc.) já existe no banco compartilhado e já foi portada para EF Core, pois a mesma Anamnese está ativa hoje no legado `portal-atlas` (`Eleva.Portal/AnamneseVirtual/`). O trabalho é, portanto, majoritariamente de **camada de serviço, API e frontend nova**, reaproveitando o schema e a regra de negócio já validada no legado — não uma feature do zero. O RBAC granular (`podeVisualizarAnamnese`/`podeEditarAnamnese`) já está pronto em ambas as pontas. A aba irmã "Atendimento" (EFC-6546, mesmo Painel do Aluno) serve de referência de padrão de camada, mas não de accordion (que não existe como shared component) nem de tratamento de erro inline (Atendimento não tem, Anamnese exige via CA-18).

## Convenções aplicáveis

1. Camadas: API (controllers sem lógica) → Domain.Services (regras) → Domain (entidades/interfaces) → Infra (EF Core). Endpoints de todas as abas do Painel do Aluno vivem em um único `PainelAlunoController.cs`.
2. DTOs de entrada/saída referenciam outras entidades por `Hash`, nunca `Id`. Parâmetros de filtro/paginação no corpo (POST), nunca querystring.
3. Autorização por `[RequiredAuthorization]` na classe do controller; checagem granular (`PodeVisualizarAnamnese`/`PodeEditarAnamnese`) dentro do service via `IValidacaoService` — já existe, apenas consumir.
4. Sem EF Migrations — schema por scripts SQL manuais. Não deve ser necessário aqui: todas as tabelas já existem.
5. `StatefulEntity`: nunca chamar `RegistrarInclusao/RegistrarAlteracao/RegistrarInativacao` diretamente — sempre via `repositorio.Insert/Update/Disable`.
6. Erros/estados inválidos via `ServiceResult<T>` — nunca `IsSuccess = true` com dados parciais.
7. `criar-service.md`: primary constructor, método privado `ValidarRequest`, sem `.Include()`, sem FluentValidation.
8. `criar-testes.md`: testes de integração herdam `BaseTest`, mockam só `IUsuarioAutenticadoRepository` e serviços externos; aguardar aprovação dos cenários antes de criar o arquivo de teste.
9. Anti-N+1: buscar em lote antes de laços, nunca query dentro de `foreach`.

## Critérios de Aceite

1. **CA-01** — Indicador "Anamnese X% respondida" / "não respondida" / "100% respondida"
2. **CA-02** — Formulário varia por segmento (Regular: 4 seções / Infantil: 7 seções)
3. **CA-03** — Primeira seção aberta por padrão, demais recolhidas; expandir/recolher livre
4. **CA-04 a CA-14** — Campos detalhados de cada seção (Regular e Infantil), com campos condicionais
5. **CA-15** — Formulário carrega respostas já salvas (aluno + ano letivo)
6. **CA-16** — Salvamento persiste no Atlas e atualiza o indicador
7. **CA-17** — Sem permissão de edição, botão "Salvar Anamnese" não aparece
8. **CA-18** — Erro no salvamento exibe mensagem inline sem perder respostas na tela
9. **CA-19** — Troca de Ano Letivo recarrega o formulário
10. **CA-20** — Accordion exibe título, ícone e contador de posição ("1 de 4")
11. **CA-21** — Toast de confirmação após salvamento bem-sucedido
12. **CA-22** — Opção "Falecido(a)" na relação com pai/mãe, sem campo condicional adicional

## Restrições e riscos

- **Banco compartilhado com portal-atlas**: qualquer alteração de dados feita por `estrutura-pedagogica` afeta o app legado e vice-versa — validar que salvar pela nova aba não quebra a leitura pelo portal-atlas enquanto ambos coexistirem.
- **Dois campos de percentual** (`AnamnesePessoa.PercentualRespondido` e `AlunoEscola.PercentualAnamnese`) precisam ser atualizados atomicamente no mesmo save — dessincronia entre eles é a causa mais provável do bug "100% com dados em branco".
- **Limpeza de campo condicional depende do frontend não enviar a pergunta** no payload de save quando a opção-gatilho é desmarcada — se o Angular mantiver o controle no `FormGroup` e só ocultar visualmente sem removê-lo do payload, o valor antigo permanece salvo no Atlas.
- **Coordenação com fix em andamento** de "campo irmão obrigatório mesmo sem irmãos" — não sobrepor lógica de perguntas repetíveis/agrupadas.
- **Migração de dados de idade** (numérico → texto) é pré-requisito de deploy e responsabilidade do time técnico — fora do escopo desta implementação, mas o formulário novo já deve assumir texto livre desde o início.
- **RBAC não deve ser simplificado**: manter `podeVisualizarAnamnese` e `podeEditarAnamnese` como checagens distintas (mais granular que Atendimento, que só tem visualizar) — decisão já validada com o usuário.
- **Componente de accordion é novo** (decisão já validada com o usuário) — não há shared component a reaproveitar; risco de retrabalho se a escolha `mat-accordion` vs. custom não for validada com o design/front antes da Fase 6.
