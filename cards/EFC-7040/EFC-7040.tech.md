# Plano Técnico — EFC-7040

> Gerado em: 2026-10-16

## Contexto

O Painel do Aluno hoje imprime Atendimento e Ocorrências com um cabeçalho simplificado (só nome da escola) e dados em lista corrida. O card pede um layout institucional (cabeçalho completo + dados em quadro/grade), reaproveitando ao máximo infraestrutura que já existe: o backend já sabe montar o cabeçalho completo (`EscolaRepository.GetCabecalhoDocumento`, já usado pelo Diário/Lista de Presença/Carômetro) — falta só expor isso ao Painel do Aluno. O trabalho real e de maior risco está no frontend: o `document-builder` (módulo compartilhado) não tem hoje nem "data ao lado do título" nem "grade multi-coluna com bordas arredondadas", e qualquer mudança nele afeta Diário, Frequência, Carômetro e Ficha Individual — que precisam continuar exatamente como estão (CA-19).

## Convenções aplicáveis

1. Backend em camadas Domain → Domain.Services → Infra → API; Domain não conhece Infra/API. Repositórios por interfaces granulares; services herdam `IBaseService`.
2. DTOs de API usam `Hash` (Guid), nunca `Id` numérico.
3. Controllers sem lógica de negócio — só delegam ao service (`Result(serviceResult)`); todo endpoint tem `/// <summary>` e `[ApiExplorerSettings(IgnoreApi = false)]`.
4. Queries de leitura simples projetam DTO direto via `Select()` no repositório — sem `.Include()`.
5. Sem EF Migrations — não se aplica aqui, não há alteração de schema.
6. Nunca adicionar comentário não pedido; comentário defasado é removido, não reescrito.
7. Componentes novos de frontend são `standalone: true`, **exceto** os do `document-builder` (`doc-header`, `doc-section`, `doc-info-row`, `doc-statement`, `doc-footer`), que são `standalone: false` via `DocumentBuilderModule` — qualquer variante nova segue esse mesmo padrão.
8. `TextMeasurable`: componentes com layout grid/flex multi-coluna **não** devem implementá-lo — exigem medição DOM real. Direto aplicável à nova grade (CA-04).
9. `frontend/src/shared/document-builder/README.md` é a fonte de verdade do module — deve ser atualizado se a API pública mudar.
10. Teste unitário Jest cobre só lógica pura; toda feature de frontend concluída exige E2E.

## Restrições e riscos

- **CA-19 é a restrição mais sensível**: os 5 componentes do `document-builder` são compartilhados com Diário, Frequência, Carômetro e Ficha Individual — qualquer mudança não estritamente opt-in quebra documentos em produção fora do escopo do card.
- **Risco de regressão de paginação**: trocar `DOC_INFO_ROW_HEIGHT` fixo por medição DOM afeta o `LayoutEngineService`/`MeasurementService` — um erro aqui pode piorar o rodapé órfão em vez de corrigi-lo. Ler esses serviços antes de mexer.
- **CA-07 exige confirmação de causa raiz** via log do viewer antes de implementar a correção — não corrigir às cegas.
- Mecanismo de logo (`CaminhoArquivoLogo`) já é URL absoluta e já funciona para o PDF via `pdfStrategy: 'backend'` — nenhum trabalho extra aqui, apenas replicar o que o Diário já faz.
- Nenhuma migração de banco — toda informação de cabeçalho já existe no schema e já é consumida por `GetCabecalhoDocumento`.
- Escopo real da Fase 4 é maior que a hipótese inicial do card sugeria: a suíte E2E de prévia de atendimento não existe — é criação, não ajuste.
