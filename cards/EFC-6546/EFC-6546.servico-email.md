# Serviço de E-mail — EFC-6546 (pendência 1.3)

> Investigação de como o envio de e-mail é feito no módulo `notas` e o que falta implementar em `estrutura-pedagogica` para usar o mesmo serviço. Gerado em: 2026-08-06.

## BUG CONFIRMADO (2026-09-15) — aba Ocorrência do Painel do Aluno nunca envia e-mail

Investigação disparada por `projetos/painel_aluno/validar_envio_email.md`: nem Atendimento nem
Ocorrência estavam enviando e-mail corretamente no Painel do Aluno, enquanto a branch
`feature/EFC-6778` (outro dev) enviava com sucesso.

### Ocorrência — causa raiz: grava numa fila morta, ninguém nunca lê

`OcorrenciaEmailService.Enviar` (`backend/EstruturaPedagogica.Domain.Services/PainelAluno/OcorrenciaEmailService.cs`)
**não usa `IEmailSender`/`IHttpMessageSender`** (o transporte real via Api de Comunicação, usado por
Atendimento). Em vez disso, faz um `Insert` direto na tabela legada `dbo.CaixaDeSaidaDeEmail`
(`_caixaDeSaidaDeEmailRepository.Insert(...)`, `ProdutoId = 171`), assumindo que algum processo
externo lê e drena essa fila depois.

Esse mecanismo é do `portal-atlas` (repo `c:/projects/portal-atlas`, classe
`CaixaSaidaDeEmails/Services/CaixaDeSaidaDeEmailService.cs`). Nele existem dois caminhos distintos:

1. `AdicionarEmail(...)` — usado por `Acesso/EnvioEmailService.cs` e `POAAgendaHangfire.cs` — **não**
   insere na tabela via EF/NHibernate; faz um POST HTTP para um serviço externo chamado "Barramento"
   (`BarramentoService.GetService("Email")` → `{internoBarramento}/api/Email/Send`, config
   `internoBarramento = https://homolog-barramento.gruposaltaedu.com/` em homolog). É esse serviço
   externo que trataria da entrega de fato.
2. `DispararEmailsPendentes()` / `EnviarEmailUsandoSendGrid(...)` — lê a tabela direto
   (`WHERE DataEnvio IS NULL AND Ativo`) e envia via SendGrid, marcando `DataEnvio`. **Este é o único
   código em todo o `c:/projects` que efetivamente lê `CaixaDeSaidaDeEmail`** — e **não está registrado
   em nenhum Hangfire recurring job nem chamado de nenhum controller/scheduled task** (`Startup.cs` do
   `portal-atlas` não tem essa entrada; busca por `DispararEmailsPendentes(` no repo inteiro só retorna
   a própria definição). É código órfão.

`OcorrenciaEmailService` não usa nenhum dos dois caminhos "corretos" do portal-atlas — insere direto
na tabela via EF, sem passar pelo Barramento e sem nada que leia depois. Resultado: a linha fica
parada para sempre com `DataEnvio = NULL`.

**Confirmado com dado real (MCP `sqlserver`, homolog, somente leitura):**
```sql
SELECT COUNT(*) Total, SUM(CASE WHEN DataEnvio IS NULL THEN 1 ELSE 0 END) SemEnvio
FROM CaixaDeSaidaDeEmail WHERE Produto = 171
-- Total=7, SemEnvio=7 (100%) — inclui uma linha criada hoje às 14:40
```
E nos últimos 180 dias, `Produto = 171` (EstruturaPedagogica) é o **único** produto que gravou nessa
tabela — nenhum outro sistema está usando esse mecanismo atualmente, reforçando que é uma integração
morta/legada, não algo que só falhou pontualmente.

**Correção recomendada:** trocar o `Insert` em `OcorrenciaEmailService.Enviar` pelo mesmo caminho já
usado por `EmailAtendimentoService` — injetar `IEmailSender` e chamar `EnviarAsync(...)`, que já vai
para a Api de Comunicação (`IHttpMessageSender.SendEmailJobAsync`). Isso também elimina a dependência
da tabela `CaixaDeSaidaDeEmail`/`_caixaDeSaidaDeEmailRepository` nesse fluxo.

### Atendimento — código está correto, suspeita é config de ambiente

Comparado `EmailSenderService.cs`/`EmailAtendimentoService.cs` desta branch (`projetos/PainelAluno`)
com `feature/EFC-6778` (commit `6ade3883d`, atualizado 2026-09-15 15:10): a lógica de transporte é
essencialmente idêntica (`HttpMessageJob.CreateBuilder` + `SendEmailJobAsync`, `ProjectId="82"`,
`ProjectName="EstruturaPedagogica"`) — EFC-6778 só troca o retorno de `bool` para um DTO
`ResultadoEnvioEmailResponse` (Aceito/Erro/ExternalId), sem mudar o mecanismo de envio. `Startup.cs`,
`AppSettings.cs`/`EmailSettings.cs` e a seção `Email` do `appsettings.json` também são idênticos entre
as duas branches.

Ou seja: **não há diferença de código que explique Atendimento falhar aqui e funcionar em
EFC-6778** — ambas fariam a mesma chamada HTTP com a mesma config. Isso aponta para causa ambiental,
consistente com a pendência já registrada mais abaixo neste documento: `Email.DeveEnviarEmail`/
`ClientKey` só estão configurados no `appsettings.json` local (`IsLocalhost: true`) e **não foram
propagados para o Secrets Manager de homolog** — se o backend testado está rodando contra homolog
deployado (não localhost), `SettingsGetter.Instance.Email` fica `null`/`DeveEnviarEmail=false` e
`EmailSenderService.EnviarAsync` retorna `false` silenciosamente (loga
`"Envio de e-mail suprimido (Email.DeveEnviarEmail=false neste ambiente)"`).

**Próximo passo sugerido:** conferir se o backend usado no teste é local (`IsLocalhost: true`) ou
homolog deployado, e olhar o log do backend no momento do envio — se aparecer o warning de supressão
acima, confirma que é a mesma pendência de Secrets Manager já rastreada aqui, não um bug de código.
Also dá pra validar via `GET /api/health/email?destinatario=...` (ver seção "Endpoint de teste rápido"
mais abaixo).

**CONFIRMADO pelo usuário (2026-09-15):** rodando o backend localmente, o e-mail de Atendimento é
enviado corretamente; no ambiente de homolog (deployado), não é enviado. Confirma exatamente a
hipótese acima — não é bug de código nesta branch, é a pendência de infraestrutura já rastreada mais
abaixo ("Falta apenas... Propagar os 4 valores... para Secrets Manager"). Ação: propagar
`Email.DeveEnviarEmail`/`Email.ClientKey` (e os demais 2 valores da seção "Falta apenas" abaixo) para
o secret `homologation/estrutura-pedagogica/parameters` — fora do escopo de código/IA.

O usuário também confirmou que essa validação foi feita **só para Atendimento** — a causa raiz de
Ocorrência (fila morta `CaixaDeSaidaDeEmail`, seção acima) é um bug de código independente, que afeta
local e homolog igualmente (a query confirmando 7/7 linhas nunca enviadas já reflete isso).

- `Remetente` (`From`) também estava desatualizado: `api.comunicacao@elevaeducacao.com.br` (domínio

- Confirmado que **não é** um problema de versão do pacote — `Eleva.Http`/`Eleva.Core` 1.7.6 (versão
  referenciada) e 1.7.6.16 (mais recente disponível no feed `CommonsLibrary`) têm exatamente o mesmo

## Resumo executivo

O e-mail da empresa **não é AWS SES nem SMTP** — é um serviço HTTP interno chamado **"Api de Comunicação"**, consumido via o pacote NuGet corporativo **`Eleva.Http`** (interface `IHttpMessageSender` do pacote `Eleva.Core`). A boa notícia: **`estrutura-pedagogica` já referencia `Eleva.Http` 1.7.6 no `.csproj` e já registra `IHttpMessageSender`/`HttpMessageSender` no `Startup.cs`** — exatamente como o `notas`. O client HTTP já existe na aplicação; só não é usado por nenhum serviço ainda. Isso torna a pendência 1.3 muito menor do que "integrar um provedor de e-mail do zero" — é essencially "usar um client que já está registrado, adicionar uma config nova, e chamar 2 métodos".

## 1. Como funciona hoje no módulo `notas`

### 1.1 Arquitetura

```
ProtocoloLancamentoEmailService.Send(...)
   → FormatEmailTemplate(...)          // busca template no banco e substitui placeholders
   → HttpMessage.CreateBuilder(...)    // monta a mensagem (from/to/subject/body)
   → IHttpMessageSender.SendEmailAsync // chama a Api de Comunicação via HTTP
```

Roda como **job assíncrono do Hangfire** (`[Queue("default")]`, `[AutomaticRetry(Attempts = 1, OnAttemptsExceeded = AttemptsExceededAction.Delete)]`) — o envio é disparado e não há confirmação síncrona de entrega para quem chamou; o método `Send` original só verifica se a chamada HTTP para *enfileirar* a mensagem retornou `200 OK`.

### 1.2 Arquivos relevantes (repo `notas`)

| Arquivo | Papel |
|---|---|
| `backend/Notas.Domain.Services/ProtocoloLancamento/ProtocoloLancamentoEmailService.cs` | Implementação concreta — monta template e chama o client |
| `backend/Notas.Domain.Services/ProtocoloLancamento/Interfaces/IProtocoloLancamentoEmailService.cs` | Contrato específico do domínio (não genérico) |
| `backend/Notas.Infra/Core/AWS/DTO/EmailSettings.cs` | DTO de configuração: `DeveEnviarEmail` (bool) + `ClientKey` (string) |

### 1.3 Registro no DI (`Startup.cs`)

```csharp
services.AddHttpClient();

services.AddHttpClient<IHttpMessageSender, HttpMessageSender>(httpClient =>
{
   httpClient.DefaultRequestHeaders.Add("x-api-key", SettingsGetter.Instance.ApiKey);
});
```

`IHttpMessageSender`/`HttpMessageSender` vêm de:
- `Eleva.Core.Interfaces.Http.CommunicationService` (interface)
- `Eleva.Http.CommunicationService` (implementação)

O header `x-api-key` usado aqui é o `ApiKey` **geral da aplicação** (o mesmo usado para outras integrações), não específico de e-mail.

### 1.4 Contrato de uso (como qualquer service chama o envio)

```csharp
var httpMessage = HttpMessage.CreateBuilder("Notas", SettingsGetter.Instance.Email.ClientKey)
   .From("api.comunicacao@elevaeducacao.com.br")
   .To(destinatarioEmail)
   .Subject(assunto)
   .Body(corpoHtml)
   .Build();

var response = await _httpMessageSender.SendEmailAsync(httpMessage);

if (response.StatusCode != HttpStatusCode.OK)
{
   // response.Result.Message traz o motivo da falha ao enfileirar
}
```

Parâmetros do builder:
- **Produto** (`"Notas"`) — nome do sistema de origem, usado pela Api de Comunicação para rastreabilidade/roteamento.
- **ClientKey** — chave de registro específica da aplicação naquela Api (não é uma credencial genérica; cada app consumidor tem a sua). Valor de homolog do `notas`: `"62b0778a0deb1397abdda0f5087ee4"` (config, não segredo crítico — mas ainda assim é identificador de app, não deve ser reaproveitado por outro sistema).
- **From** — remetente usado hoje pelo `notas`: `api.comunicacao@elevaeducacao.com.br` (endereço genérico/corporativo, não por-app).
- **To / Subject / Body** — padrão de e-mail transacional simples; `Body` aceita HTML.

O retorno de `SendEmailAsync` é um `HttpStatusCode` + `Result.Message` — ou seja, o que a chamada confirma é que a mensagem **foi aceita na fila** da Api de Comunicação, não necessariamente que o destinatário já recebeu. Não há callback/webhook de entrega observado nesta investigação.

### 1.5 Templates

O `notas` mantém uma tabela `TemplateEmail` com textos cadastrados (identificados por um enum, ex. `TemplateEmailEntity.ProtocoloLancamento`), com placeholders (`@protocolo`, `@data`, `@avaliacao`, etc.) substituídos em código antes de montar o `Body`. Isso é uma opção arquitetural do `notas`, não uma exigência do client `IHttpMessageSender` — o client só recebe uma string de `Body` já pronta.

## 2. Estado atual em `estrutura-pedagogica`

### 2.1 O que já existe (e é reaproveitável sem trabalho extra)

- **`Eleva.Http` já está referenciado** no `.csproj` (`backend/EstruturaPedagogica.Infra/EstruturaPedagogica.Infra.csproj`, mesma versão 1.7.6 do `notas`).

- Ou seja: **o client HTTP para a Api de Comunicação já está pronto para ser injetado em qualquer service** — não precisa adicionar pacote nem alterar `Startup.cs`.

### 2.2 O que falta

1. **Configuração de e-mail no `AppSettings`:** `EstruturaPedagogica.Infra/Core/AWS/DTO/AppSettings.cs` tem `Twilio`, `Hangfire`, `S3Bucket`, `Folha`, `Produto`, `ElevaId`, mas **não tem nenhuma seção `Email`**. Falta:
   - Criar um DTO equivalente ao `EmailSettings` do `notas` (`DeveEnviarEmail: bool`, `ClientKey: string`).
   - Adicionar a propriedade `EmailSettings Email { get; set; }` em `AppSettings`.
   - Adicionar a seção `"Email": { "DeveEnviarEmail": ..., "ClientKey": "..." }` no `appsettings.json` (e nos demais ambientes/secrets, conforme o padrão do repo).
2. **ClientKey própria do `estrutura-pedagogica`:** a chave usada pelo `notas` é específica daquele app registrado na Api de Comunicação. `estrutura-pedagogica` precisa da **sua própria ClientKey** — isso é uma solicitação ao time responsável pela Api de Comunicação (provavelmente o mesmo time de infra/plataforma), não uma decisão de código.
3. **Substituir o corpo de `EmailSenderService.EnviarAsync`** (`backend/EstruturaPedagogica.Domain.Services/EnvioEmail/EmailSenderService.cs`) para:
   - Injetar `IHttpMessageSender` (já disponível via DI) no construtor, no lugar/além do `ILogger`.
   - Montar o `HttpMessage` via `HttpMessage.CreateBuilder("EstruturaPedagogica"[ou nome de produto correto], SettingsGetter.Instance.Email.ClientKey)` com `.From(...).To(destinatarioEmail).Subject(assunto).Body(corpoHtml).Build()`.
   - Chamar `await _httpMessageSender.SendEmailAsync(httpMessage)` e retornar `response.StatusCode == HttpStatusCode.OK`.
   - **Manter a assinatura atual de `IEmailSender.EnviarAsync(string destinatarioEmail, string assunto, string corpoHtml) : Task<bool>`** — o contrato já é compatível com o que o client precisa (destinatário, assunto, corpo), então `EmailAtendimentoService` não precisa de nenhuma alteração.
4. **Definir o remetente ("From")** a usar — reaproveitar `api.comunicacao@elevaeducacao.com.br` (mesmo do `notas`) ou usar um remetente específico do Painel do Aluno/estrutura-pedagogica — decisão a confirmar com o time de comunicação/produto.
5. **Decidir se o envio é síncrono (como proposto acima) ou assíncrono via Hangfire (como o `notas` faz):** o `notas` enfileira o envio como job Hangfire e não confirma entrega de forma síncrona. Mas o CA-26 do EFC-6546 exige que o card indique, no momento do salvamento, **se o e-mail foi enviado e para quem** (`EmailEnviadoResponsavelPedagogico/Financeiro`) — isso pressupõe uma confirmação síncrona (ou near-síncrona) no fluxo de salvar o atendimento. `EstruturaPedagogica` já tem Hangfire configurado (`AppSettings.Hangfire`), então o padrão do `notas` **poderia** ser replicado, mas isso mudaria a semântica de CA-26 (o campo de auditoria passaria a refletir "enfileirado", não "confirmado no destino"). **Recomendação:** manter chamada síncrona a `SendEmailAsync` dentro de `EmailSenderService.EnviarAsync` (como já estruturado por `EmailAtendimentoService` hoje), já que o retorno de `SendEmailAsync` já é rápido (só confirma o aceite na fila da Api de Comunicação, não a entrega final) — não é uma chamada de longa duração que justifique um job em background.

### 2.3 O que **não** precisa ser feito (diferente do que a pendência original supunha)

O comentário em `EmailSenderService.cs` (linhas 7-26) que descreve o caminho "AWS SES" está **desatualizado** e deve ser substituído por este documento como referência.

## 4. Riscos e decisões abertas

1. **ClientKey e nome de produto ainda não existem para `estrutura-pedagogica`** — depende de ação de outro time (não é algo que a IA ou o desenvolvedor resolvam sozinhos no código). Bloqueia o passo 1 do plano acima.
2. **Remetente ("From") a usar** — decidir se reaproveita o endereço genérico do `notas` ou usa um remetente próprio; impacta a percepção do destinatário (quem "envia" o e-mail de Atendimento).
3. **Semântica de CA-26 (síncrono vs. enfileirado)** — conforme discutido em 2.2.5, a interpretação de "enviado" precisa ser alinhada: confirmação de aceite na fila (o que este client oferece) vs. confirmação de entrega real (que não existe hoje em nenhum lugar observado, nem no `notas`). Vale alinhar a expectativa com produto para não prometer mais do que o serviço garante.
4. **Sem tabela de template no `estrutura-pedagogica`** (pendência 1.4, já registrada em `EFC-6546.pendencias.md`) — isso é independente da integração com a Api de Comunicação; o texto do e-mail continua sendo montado em código, só o *transporte* muda.
5. **Ambiente de homolog/produção da Api de Comunicação** — não foi possível confirmar nesta investigação (limitada à leitura de código) se a Api de Comunicação tem endpoints/chaves distintos por ambiente, ou se há throttling/quota por ClientKey — validar com o time responsável ao solicitar o cadastro.
