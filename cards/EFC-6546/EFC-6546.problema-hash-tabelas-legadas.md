# EFC-6546 — Problema: tabelas legadas de Atendimento sem coluna `Hash`

**Status:** ✅ decidido — Opção A. Script criado em `backend/Scripts/EFC-6546-hash-tabelas-legadas-atendimento.sql`, ainda não executado no banco.
**Descoberto em:** 2026-08-11, ao investigar o erro `Invalid column name 'Hash'` no endpoint `GetSolicitantesAtendimento`.

## Resumo

Todo o código escrito para EFC-6546 (T2, T4, T5, T6, T7) assume a convenção padrão do `estrutura-pedagogica`: toda entidade é `BaseEntity`/`StatefulEntity`, sempre tem uma coluna `Hash` (`uniqueidentifier`), e todo DTO/request troca `Hash`, nunca `Id` bruto.

Isso é verdade para `Atendimento` e `TipoPublicoAtendido` (ambas têm `Hash` de fato, confirmado via `sys.columns`). **Não é verdade** para o restante das tabelas de referência/apoio do módulo de Atendimento — elas são tabelas legadas (herdadas de uma era anterior à convenção de Hash) e simplesmente não têm essa coluna:

| Tabela | Tem `Hash`? |
|---|---|
| `Atendimento` | ✅ sim |
| `TipoPublicoAtendido` | ✅ sim |
| `SolicitanteAtendimento` | ❌ não |
| `MotivoAtendimento` | ❌ não |
| `TipoAtendimento` | ❌ não |
| `MotivoAtendimentoTipoPublicoAtendido` | ❌ não |
| `FormularioAtendimento` | ❌ não |
| `FormularioAtendimentoQuestao` | ❌ não |
| `FormularioAtendimentoQuestaoOpcao` | ❌ não |
| `FormularioAtendimentoResposta` | ❌ não |
| `FormularioAtendimentoRespostaOpcao` | ❌ não |
| `AtendimentoPessoa` | ❌ não |

(Confirmado via `SELECT ... FROM sys.columns c JOIN sys.types t ...` rodado pelo usuário em 2026-08-11 — o `db_map` deste repositório não guarda tipos/existência de coluna, só nomes de tabela, então essa informação não estava disponível antes de consultar o banco ao vivo.)

As entidades C# (`SolicitanteAtendimento.cs`, `MotivoAtendimento.cs`, `TipoAtendimento.cs`, `FormularioAtendimento*.cs`, `AtendimentoPessoa.cs`) foram modeladas como `BaseEntity`/`StatefulEntity` normais (sempre com propriedade `Hash`), e os mappings chamam `IsBaseEntity()`/`IsStatefulEntity()` sem o parâmetro `hasHash: false` — então o EF Core sempre tenta ler/gravar uma coluna `Hash` que não existe fisicamente.

## Onde já quebra (confirmado) e onde vai quebrar (previsto, ainda não testado)

**Confirmado (erro relatado pelo usuário):**
- `GET /painelaluno/getsolicitantesatendimento` → `SolicitanteAtendimentoRepository.GetResponse()` seleciona `x.Hash` → `Invalid column name 'Hash'`.

**Previsto — mesmo padrão exato, ainda não exercitado pelo usuário:**
- `GET /painelaluno/gettiposatendimento/{hash}` → `TipoAtendimentoRepository.GetPorPublico()` seleciona `x.Hash`.
- `GET /painelaluno/getmotivosatendimento/{hash}/{hash}` → `MotivoAtendimentoRepository.GetPorTipoEPublico()` seleciona `x.Hash` e `x.TipoAtendimento.Hash`.
- `GET /painelaluno/getnorteadoratendimento/{hash}/{hash}/{hash}` → `FormularioAtendimentoRepository.GetNorteadorPorCombinacao()` seleciona `Hash` de `FormularioAtendimento`, `FormularioAtendimentoQuestao`, `FormularioAtendimentoQuestaoOpcaoCondicional` e `FormularioAtendimentoQuestaoOpcao` — **4 colunas inexistentes na mesma query**.
- `POST /painelaluno/salvaratendimento` (`AtendimentoSaveService`):
  - `ValidarCampos`: `_solicitanteAtendimentoRepository.GetIdByHash(...)`, `_tipoAtendimentoRepository.GetIdByHash(...)`, `_motivoAtendimentoRepository.GetByHash(...)` — todos filtram `WHERE Hash = ...`, coluna inexistente.
  - `MontarRespostas`: `_formularioAtendimentoQuestaoRepository.GetByHash(hashesQuestoes)`, `_formularioAtendimentoQuestaoOpcaoRepository.GetByHash(hashesOpcoes)` — mesmo problema.
  - `Insert(atendimento)` (com `FormularioAtendimentoRespostas` aninhadas) e `Insert(pessoasVinculadas)` (`AtendimentoPessoa`): o EF Core vai gerar `INSERT` incluindo a coluna `Hash` (mapeada por convenção, `IsRequired()`), que não existe → mesmo erro, agora em escrita.

Ou seja: **nenhuma parte do fluxo de salvar um atendimento (T4/T7) funciona hoje**, e as telas de seleção de Tipo/Motivo/Solicitante/Norteador (T2/T7) também vão falhar assim que o usuário testar além do que já testou.

## Por que isso não apareceu antes

`GetAtendimentos` (a única parte do fluxo já testada com sucesso) usa uma projeção estreita — `AtendimentoRepository.GetResponseParaPainelAluno` monta DTOs (`AtendimentoResponse`, `PerguntaRespondidaAtendimentoResponse`, `AtendimentoPessoaPapelNomeDTO`) que **não têm campo `Hash`** para essas sub-entidades, então o EF nunca tentou ler essa coluna ali. Os outros endpoints/fluxos citados acima leem ou escrevem via `Hash` diretamente, por isso quebram.

## Duas opções de correção

### Opção A — Adicionar a coluna `Hash` via script SQL

`ALTER TABLE [dbo].[<Tabela>] ADD [Hash] UNIQUEIDENTIFIER NOT NULL DEFAULT NEWID();` + `CREATE UNIQUE INDEX` (ou `CONSTRAINT UQ_..._Hash UNIQUE`), em cada uma das 10 tabelas listadas sem `Hash`.

- **A favor:** nenhuma linha de código de T2/T4/T5/T6/T7 muda — o C# já espera `Hash` em todo lugar. Mantém a convenção "sempre Hash" do resto do sistema.
- **Contra:** é uma migração de schema real em tabelas legadas que podem ser lidas por outros sistemas (ex.: `portal-atlas`, se ainda ativo sobre o mesmo banco) — adicionar coluna é uma operação segura/retrocompatível em si (não quebra leitores existentes), mas ainda é uma mudança de banco que merece revisão antes de rodar em produção.
- **Sem precedente direto neste repo:** os 2 scripts existentes que criam coluna `Hash` (`EFC-5808...`, `EFC-6515...`) fazem isso em `CREATE TABLE` de tabelas novas, não em `ALTER TABLE` de tabelas legadas pré-existentes.

### Opção B — Usar `Id` (int) direto nessas tabelas, sem Hash

Não toca o banco. Passa a expor o `Id` inteiro dessas 10 tabelas nos DTOs/requests, em vez de `Hash` (Guid) — ex.: `SalvarAtendimentoRequest.HashSolicitanteAtendimento` (Guid) → `SolicitanteAtendimentoId` (int) direto no contrato da API.

- **A favor:** nenhuma mudança de banco.
- **Contra:** exige refatorar bastante código já implementado: DTOs de request/response (`SalvarAtendimentoRequest`, `RespostaNorteadorRequest`, `MotivoAtendimentoResponse`, `NorteadorAtendimentoResponse`, `PerguntaAtendimentoResponse`, etc.), os métodos dos repositórios (`GetByHash`→`GetById` ou equivalente), o `painel-aluno.service.ts` e os `models.ts` do frontend, e os componentes Angular (`atendimento-tab.component.ts/html`) que hoje tratam essas opções como `{hash, descricao}`. Quebra a convenção "nunca expor Id bruto" seguida no resto do app — embora o risco de segurança real seja baixo aqui (são catálogos fixos/pequenos — Tipo de Atendimento, Motivo, Solicitante —, não dados de aluno/pessoa; o mesmo raciocínio já vale para `TipoQuestaoAtendimentoEnum`, hoje exposto como inteiro puro ao frontend sem Hash).

## Observação

Poderia haver uma opção híbrida (Hash só nas tabelas realmente expostas por hash em alguma tela — ex. manter Id interno para `FormularioAtendimentoQuestao`/`Opcao` que já hoje viajam para o frontend só dentro de uma resposta aninhada, mas adicionar Hash só em `SolicitanteAtendimento`/`MotivoAtendimento`/`TipoAtendimento` que aparecem em dropdowns simples) — não detalhada aqui porque não foi pedida, mas pode valer a pena considerar ao decidir.

## Decisão

**Opção A escolhida (2026-08-11).** Script `backend/Scripts/EFC-6546-hash-tabelas-legadas-atendimento.sql` criado — `ALTER TABLE ... ADD [Hash] UNIQUEIDENTIFIER NOT NULL DEFAULT NEWID(), CONSTRAINT UQ_..._Hash UNIQUE ([Hash])` para as 10 tabelas listadas acima. `DEFAULT NEWID()` preenche automaticamente um Hash único para cada linha já existente no momento do `ALTER TABLE` — não há etapa manual de backfill.

Nenhuma mudança de código C# foi necessária: os 10 mappings (`SolicitanteAtendimentoMap`, `MotivoAtendimentoMap`, `TipoAtendimentoMap`, `MotivoAtendimentoTipoPublicoAtendidoMap`, `FormularioAtendimentoMap`, `FormularioAtendimentoQuestaoMap`, `FormularioAtendimentoQuestaoOpcaoMap`, `FormularioAtendimentoRespostaMap`, `FormularioAtendimentoRespostaOpcaoMap`, `AtendimentoPessoaMap`) já usam `IsBaseEntity()`/`IsStatefulEntity()` no modo padrão (`hasHash: true`), então já esperavam a coluna — só faltava ela existir no banco.

**Próximo passo:** rodar o script no banco (mesma ressalva de sempre — não posso executar DDL, só o usuário/time com acesso de escrita).
