# Plano Técnico — EFC-6733

> Gerado em: 2026-09-10

## Contexto

O refinamento pede um toggle "Visualizar apenas as suas turmas" na listagem de lançamento de frequência, visível só para quem tem visão de coordenação e possui alguma alocação no resultado. Hoje o backend já calcula essa alocação — mas só quando o usuário **não** tem visão de coordenação, e usa isso para **filtrar** a query (`FiltrarPorAlocacao` e o `Where` condicional de `GetEventosParaFrequencia`). A implementação consiste em tornar esse cálculo **sempre presente** (sem alterar o filtro condicional existente, que deve continuar intacto para não regredir CA-13), expor o resultado como uma flag aditiva nos DTOs de resposta, e no frontend usar essa flag para filtrar client-side a listagem já carregada — sem nova chamada ao backend, conforme os Complementos Técnicos do card.

O toggle é modelado como estado próprio do `ListarComponent` (fora do `form` do filtro da tela), pelos motivos detalhados em "Restrições e riscos".

## Convenções aplicáveis

1. Sem comentários no código, salvo regra intrínseca não óbvia pelo nome.
2. Nunca filtrar `Ativo` manualmente fora dos métodos de acesso já usados no repositório (`x.Professores.Any(p => p.Ativo && ...)` já é o padrão local).
3. Sem FluentValidation, sem EF Migrations — schema via scripts manuais (não se aplica aqui, não há alteração de schema).
4. Todo método público novo e toda ramificação condicional relevante exige teste de integração.
5. `<summary>` XML obrigatório em controllers; fora deles só quando a regra não é dedutível do nome. Nenhum controller/endpoint novo nesta feature.
6. Frontend: componentes novos são `standalone: true`; campos de `dynamic-components` recebem `[control]` direto; toggle nativo é proibido — usar `<app-toggle>` (`shared/dynamic-components/toggle/toggle.component.ts`), que aceita `[control]: FormControl` e `[toggleInfo]: string` de forma standalone, sem depender do sistema de filtro.
7. Services HTTP sempre com `catchError(HandleApiError)`; nunca `console.error`/`alert`.
8. Testes: Jest para lógica de componente (classe local espelhando métodos, sem TestBed/Jasmine) em `tests/unit/lancamento-frequencia/`; testes de integração .NET em `GetEventosServiceTests.cs`, seguindo `Padrão para testes de Integração.md` (repositórios sempre `AddTransient`, nunca mockados; `UsuarioAutenticadoRepository` mockado com `IdUsuarioAutenticado`).
9. HTML do `estrutura-pedagogica` prioriza shared/dynamic components — `app-toggle`, não `<input type="checkbox">`.

## Critérios de Aceite

1. **CA-01:** Controle "Visualizar apenas as suas turmas" exibido na listagem.
2. **CA-02:** Exibido só quando o usuário tem visão de coordenação E possui alocação em ao menos uma turma/disciplina do resultado.
3. **CA-03:** Inicia desativado, listagem mostra todas as turmas.
4. **CA-04:** Ativado, chamada por dia/turno → turmas com qualquer alocação do usuário.
5. **CA-05:** Ativado, chamada por tempo de aula → turmas com aula da disciplina do usuário.
6. **CA-06:** Ativado, tela de lançamento por tempo de aula → só os tempos da alocação do usuário disponíveis.
7. **CA-07:** Ativado, navegação entre turmas percorre só a listagem filtrada.
8. **CA-08:** Ativado, contagem/totalizadores refletem só as turmas exibidas.
9. **CA-09:** Combina com demais filtros e busca — interseção.
10. **CA-10:** Desativar volta a exibir tudo, sem nova consulta.
11. **CA-11:** Estado do controle persistido entre acessos.
12. **CA-12:** Sem turmas após filtro → mensagem de resultado vazio já existente.
13. **CA-13:** Não regressão para quem não ativa o controle, não tem alocação, ou não tem visão de coordenação.

## Restrições e riscos

- **Decisão de arquitetura do toggle (já validada com o usuário):** o toggle vive como estado próprio do `ListarComponent`, fora do `form`/`FilterConfig` da tela. Motivo: `FiltroComponent.value<T>()` sempre retorna `form.getRawValue()`, então qualquer campo do `filters[]` vazaria no payload enviado ao backend — contrariando o complemento técnico do card ("o estado do controle não é enviado no payload"). Além disso, a visibilidade do controle (CA-02) depende do resultado da consulta (`eventos.some(e => e.possuiAlocacao)`), o que o sistema declarativo de `dependency_list`/`watch_list` do `FiltroComponent` não suporta hoje (ele reage a mudanças de outros campos do form, não a dados de resposta).
- **CA-13 é o principal risco de regressão:** os filtros condicionais já existentes (`FiltrarPorAlocacao` e o `Where` de `GetEventosParaFrequencia`) devem permanecer absolutamente inalterados — a nova flag é só uma projeção adicional na mesma query, nunca um novo filtro. Os testes já existentes na região `#region Testes de Professor` não podem quebrar.
- **Propagação de estado entre listagem e tela de lançamento (CA-06):** resolvida recortando `evento.tempos` antes de gravar no `ListaFrequenciaStore`, em vez de propagar o booleano `apenasMinhasTurmas` — mais simples e evita acoplar `LancamentoFrequenciaComponent` ao estado do toggle da listagem. Validar durante a implementação se `temposDisponiveis` de fato deriva de `temposRelacionados`.
- **Sem breaking changes de contrato:** os novos campos (`PossuiAlocacao`/`possuiAlocacao`) são aditivos em DTOs já existentes — não quebram consumidores atuais do endpoint `get-eventos`.
- **`criar-filtro` não se aplica integralmente:** o command é um processo completo para criar um filtro novo do zero (enum de passo, `FilterRequest`, repositório de filtro, endpoints `filter-{passo}`); esta feature não cria filtro nem passo novo, então o processo completo do command não é seguido — só o padrão de nomenclatura `FieldType.Toggle` foi considerado como referência, mas não adotado literalmente (ver decisão de arquitetura acima).
